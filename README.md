# VPN-клиент для Android и iOS

**Рабочий OpenVPN-клиент: Kotlin и Jetpack Compose на Android, Swift-пакеты на iOS, собственный JNI-мост к OpenVPN 3, живой API, CI и подписанные релизы.**

> **Коротко.** Обычный VPN-клиент рисует зелёное «защищено», как только поднялся системный интерфейс, — хотя трафик может идти мимо туннеля. Здесь статус «защищено» невозможно сконструировать без измеренного доказательства, а при сомнении приложение честно говорит «подключено». Android-клиент работает на реальном движке, входит через живой API, обновляет себя и раздаётся подписанными APK; iOS пока представлен Swift-пакетами без app-таргета.

**Ссылки:** [релизы и APK](https://github.com/impossi8le/vpn-client-app/releases) · [документация](docs/) · [скриншоты прогонов](docs/testing/) · [архитектура Android](docs/architecture/2026-10-03-android-architecture.md)

## Проблема

- Пользователь не может проверить, куда идёт его трафик. Системный флаг «VPN активен» означает только то, что поднят интерфейс; трафик при этом может уходить через Wi-Fi.
- Клиент, который выводит зелёный статус из этого флага, приучает не осторожничать. Это худший класс ошибки в security-продукте: ложное спокойствие вместо сигнала.
- Раздача через Google Play требует аккаунта и ревью, а закрытому сервису нужен собственный канал и понятное обновление без магазина.
- Android и iOS должны жить по одному контракту API, иначе бэкенд обрастает платформенными ветвлениями.
- Профиль `.ovpn` приходит с сервера и является недоверенным входом: приватный ключ нельзя логировать, а параметры нельзя применять вслепую.

## Что умеет

- Подключается по OpenVPN 3 через собственный JNI-мост: `libovpn3.so` собирается под arm64-v8a и x86_64 и лежит внутри APK.
- Входит по одноразовой ссылке с подтверждением в Telegram: приложение опрашивает сессию и получает токен.
- Показывает список конфигов с сервера, кэширует его в `filesDir` и при сбое сети отдаёт последний известный список, а не пустой экран.
- Санитизирует серверный `.ovpn` перед применением и не пишет секреты профиля в логи и отчёты.
- Обходит РФ-сервисы: сервер отдаёт подсети и каталог сервисов, приложение применяет `excludeRoute` на API 33+, а на API 26–32 честно отказывает.
- Обновляется внутри себя: проверяет версию, скачивает подписанный APK, ставит поверх и блокирует сборки ниже `min-supported`.
- Гасит статус «подключено», если сеть с транспортом VPN пропала: сторож опрашивает состояние раз в 5 секунд.
- Плитка быстрых настроек, foreground-сервис с уведомлением и экран диагностики: буфер логов ядра, скруббер секретов, обезличенный профиль и отправка отчёта в поддержку.

## Как это устроено

Это два клиента над одним сервисным контрактом, а не кроссплатформенное приложение. Общий у них протокол API и понятия домена, код — разный.

Android разбит на 16 модулей, и направление зависимостей проверяется структурой сборки:

```text
:app
 ├─ :feature:auth  :feature:home  :feature:configs  :feature:account  :feature:bypass
 │    └─ :core:domain, :core:ui
 ├─ :core:network  :core:config  :core:security  :core:tunnel  :core:protection
 │    └─ :core:domain
 └─ :vpnservice ─── :core:config + :vpnengine (OpenVPN 3, JNI)
```

`core:domain`, `core:config` и `core:network` — чистый Kotlin/JVM: их тесты идут без эмулятора. Остальные `core:*` — Android-библиотеки-адаптеры. `:vpnservice` владеет foreground-сервисом и строит TUN; `:vpnengine` упаковывает нативное ядро и переводит его события в доменные состояния.

Приложение общается с бэкендом ровно через четыре эндпоинта: `POST /auth/link`, `POST /auth/poll`, `GET /me`, `GET /config/{id}`. Статус защиты сервер не отдаёт принципиально — он собирается на устройстве из измеренных фактов. Один HTTP-статус `403` клиент различает по `error.code` (`account_blocked`, `config_revoked`, `subscription_expired`), поэтому ответ без кода считается неожиданным.

Обновление идёт от собственного сервера версий, GitHub Release — запасной канал. Действующий минимум хранится в `min-supported.txt` (сейчас `157`) и на сервере; сборка ниже порога запирает `ForceUpdateScreen`, не рисуя навигацию.

iOS состоит из Swift-пакетов: `CoreDomain` с портами, `CoreNetwork`, `CoreConfig`, `CoreSecurity`, `CoreUI`, `FeatureAuth`, `FeatureHome`, `TunnelKitCore` и тестовые двойники. Пакеты собираются и тестируются в CI; app-таргет, подпись и TestFlight требуют macOS и отдельного Xcode-проекта.

### Вход и сессия

Вход устроен как одноразовая ссылка: клиент создаёт попытку, показывает ссылку на подтверждение в Telegram, опрашивает `POST /auth/poll` и получает токен только после подтверждения на стороне бота. Сессия хранится в Android Keystore или Keychain, а не в открытых настройках. На экране ожидания есть явно названная кнопка «Демонстрация», потому что без настоящего подтверждения экраны после входа иначе не проверить; она не выдаёт себя за состоявшийся вход.

### Подключение и честный статус

`VpnService` строит TUN, `:vpnengine` отдаёт события нативного ядра, `core:tunnel` переводит их в доменный статус. Отдельный `TunnelPresenceWatcher` раз в 5 секунд проверяет наличие сети с транспортом VPN и гасит «подключено», если интерфейс исчез. Экран подключения — один маршрут на восемь состояний: они различаются текстом, цветом кольца и действием кнопки, но не составом, чтобы маршрут нельзя было расставить неверно относительно состояния туннеля.

### Экраны

В `AppDestination.kt` 14 маршрутов: Startup, Login, LoginWaiting, Connection, Bypass, Account, NoSubscription, AccessRevoked, HowToEnableVpn, About, Feedback, ThirdPartyLicenses, TileHowTo, Demo. Число 18 из `docs/design/mockup.html` относится к исходному макету и помечено устаревшим; актуальная спека — `docs/design/2026-10-06-implemented-ui-spec.md`.

### Профиль как недоверенный вход

Серверный `.ovpn` проходит разбор и санитизацию до записи в приватный каталог приложения. `LogScrubber` вычищает секреты из логов, `ConfigAnonymizer` обезличивает профиль перед отправкой отчёта, `LogRepeatCollapser` не даёт буферу разрастись повторами. Приватный ключ не передаётся через intent: профиль кладётся в `filesDir` приложения.

### Доставка и обновление

Собственный сервер отдаёт страницу с номером версии, APK и инструкцией по предупреждению Play Protect; файл поддерживает `Range`, поэтому докачка не обрывается. GitHub Release с тегом `android-v<versionCode>` остаётся запасным каналом. Порог `min-supported` клиент берёт с сервера, а запасной путь через GitHub читает `min-supported.txt` из корня; job релиза увеличивает `versionCode`, иначе APK не встанет поверх предыдущего.

## Инженерные находки

- **Зелёный статус невозможно подделать типом.** `ConnectionStatus.Protected` требует `ProtectionEvidence`, конструктор которого `internal`, а создать evidence умеет только `ProtectionVerdict.evaluate` из трёх подтверждённых фактов. Ответ сервера или системный флаг не могут породить зелёный статус — это ограничение компилятора, а не соглашение.
- **Молчание пробы трактуется как провал.** Если `ProtectionProbe` бросил исключение, `ProtectionGate` возвращает `ProtectionFailed(ProbeUnavailable)`, а не оставляет предыдущее зелёное состояние. «Не смогли проверить» — это не «безопасно».
- **Неудачный рефреш не стирает кэш.** `cacheAfterRefresh(current, fetched) = fetched ?: current`: любая сетевая ошибка сохраняет последний хороший список и лишь помечает его устаревшим. Решение вынесено в чистую функцию и покрыто тестом, потому что это выбор «хоронить данные или нет».
- **CI падает, если тесты не выполнились.** Отдельный шаг считает `tests="..."` в XML-отчётах и возвращает ошибку при нуле. Причина конкретная: JUnit 5 в Android-модуле без `useJUnitPlatform()` даёт зелёную сборку с нулём тестов, а `testDebugUnitTest` вообще не видит тесты чистых JVM-модулей.
- **Отказ от вендоринга ics-openvpn.** Это `android.application`, а не библиотека; JitPack публикует APK, форки не выделили AAR, а `co.pango:openvpn-aar` оказался оболочкой с `classes.jar` в 22 байта. Выбран OpenVPN 3 под MPL 2.0 и свой мост; сначала отдельный `openvpn3-spike.yml` ответил на вопрос «собирается ли», и только потом ядро вошло в основной CI.
- **Обновление ломалось на таймауте, а не на сети.** Скачивание 106-МБ APK шло клиентом с `callTimeout(45s)`, который обрывал поток на середине. Введён отдельный клиент без этого таймаута; заодно LOAD-сегменты `libovpn3.so` выровнены на 16 КБ (`0x4000`) под требование Android 16 и сверены `readelf` на отгруженной сборке.

## Быстрый старт

```bash
git clone https://github.com/impossi8le/vpn-client-app.git
cd vpn-client-app/android

# JDK 17 обязателен; JDK 21 из Android Studio не подходит для jvmToolchain(17)
JAVA_HOME=/path/to/jdk17 ./gradlew test --no-daemon
JAVA_HOME=/path/to/jdk17 ./gradlew :app:assembleDebug --no-daemon
```

Поднять эмулятор и поставить последний APK из CI:

```bash
scripts/run-emulator.sh
```

Поставить APK на подключённый по USB телефон (нужен только `adb`):

```bash
scripts/install-apk.sh
```

Установка Android SDK/NDK и восстановление тулчейна описаны в `scripts/local-build.md`. Профиль для ручной проверки кладётся в приватный каталог приложения через `run-as`, а не через intent: текст с приватным ключом не должен ходить между процессами.

## Требования к сборке

| Компонент | Требование |
|---|---|
| JDK | 17 (Temurin). JDK 21 из Android Studio не заменяет его: `jvmToolchain(17)` не находит тулчейн под 21-м |
| Android SDK | platform 35 и build-tools 35.x; NDK и CMake нужны модулю `:vpnengine` |
| adb | только для `scripts/install-apk.sh`; JDK, Gradle и SDK при этом не требуются |
| iOS | Swift-пакеты собираются и тестируются там, где это поддерживает тулчейн (включая Windows); app-таргет, подпись и TestFlight — только на macOS с Xcode |
| Подпись | ключ релиза лежит в секретах CI; локальная debug-сборка подписывается debug-ключом |

## Ручная проверка на устройстве

```bash
adb push <profile>.ovpn /data/local/tmp/p.ovpn
adb shell "run-as com.impossi8le.vpnapp cp /data/local/tmp/p.ovpn files/profile.ovpn"
adb logcat -s VpnTunnel
```

Профиль копируется в приватный каталог приложения, а не передаётся через intent. Логи ядра пишутся под тегом `VpnTunnel`: там видно каждое событие и точную причину отказа, тогда как в интерфейсе без них остаётся только «туннель не поднялся».

## Что не входит

- Публикация в Google Play и App Store: раздача идёт своим каналом, магазины в проекте не настроены.
- Аккаунты, подписки и биллинг: клиент различает коды `subscription_expired` и `account_blocked`, но самим биллингом не занимается.
- Серверная часть: в репозитории только страница раздачи `server/app_feed/index.html`; API и бот живут отдельно.
- Десктопные клиенты и веб-версия.

## Статус и ограничения

- **Android работает.** В репозитории 57 релизов; последний — `android-v159` от 22 ноября 2026, APK около 59 МБ. Действующий `min-supported` — `157`.
- **Тесты.** В дереве 94 файла в `src/test`, 20 инструментальных и 20 Swift-тестов. Зафиксированный прогон 2026-10-06 — 476 JVM-тестов без падений; после релиза v159 это число не перепроверялось.
- **Проба защиты остаётся заглушкой.** Поэтому зелёного «защищено» в интерфейсе нет намеренно: показывать непроверенный исход как факт запрещено тем же инвариантом.
- **Обход РФ-сервисов проверен не до конца.** Серверная часть и применение `excludeRoute` реализованы, но подтверждения на устройстве, что трафик действительно уходит с `tun0`, нет.
- **iOS — только пакеты.** Xcode-проекта `Apps/VpnApp/*.xcodeproj` в репозитории нет, поэтому job «Archive → TestFlight» в `ios.yml` пропускается по условию; сборка, подпись и туннель на устройстве требуют macOS/iPhone.
- **Лицензия расходится с кодом.** `LICENSE` — GPL-2.0, но используемые движки (MPL 2.0 и GPLv3 с исключением Apple) не требуют GPLv2. Расхождение зафиксировано в документации; смена лицензии опубликованного проекта — решение владельца.
- **Документация местами отстаёт.** `android/README.md` говорит о 10 маршрутах, в `AppDestination.kt` их 14; число экранов в старом макете (18) относится к исходному дизайну, а не к реализации.
- **Раздача вне магазинов.** Play Protect предупреждает при установке, приложение объясняет, как пройти предупреждение; это ожидаемая цена собственного канала.

## Вопросы и короткие ответы

- **Нужен ли Google Play?** Нет. APK раздаётся с собственного сервера, GitHub Release — запасной канал. Play Protect предупреждает при установке; порядок обхода описан в `docs/architecture/2026-10-15-play-protect-install-instruction.md`.
- **Почему статус не зелёный, если туннель поднят?** Поднятый интерфейс не доказывает, что трафик пошёл через него. Проба защиты пока заглушка, а тип не позволяет собрать зелёный статус из системного флага.
- **Какие версии Android поддерживаются?** `minSdk = 26`, `targetSdk = 35`. Обход РФ-сервисов через `excludeRoute` доступен только с API 33; на 26–32 приложение честно отказывает.
- **Почему Android и iOS — два проекта, а не Kotlin Multiplatform?** Платформенные VPN API и движки разные; общий у клиентов контракт API и понятия домена, а не код. Кроссплатформенность здесь дала бы только общие DTO.
- **Можно ли собрать iOS на Windows?** Часть Swift-пакетов собирается и тестируется на Windows (`swift build`, `swift test` — там, где тулчейн это поддерживает); app-таргет, подпись и TestFlight требуют macOS.
- **Где ключ подписи?** Вне git, в секретах CI; потеря необратима. Процедура — `docs/architecture/2026-10-06-signing-and-release.md`.
- **Почему в репозитории нет готового Xcode-проекта?** iOS пока доведён до пакетов с тестами; job архивации включается сам, когда появится `Apps/VpnApp/*.xcodeproj`.
