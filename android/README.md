Android собран именно так. Мост пишем сами; перед кодом — проверка сборки под

## Как получить APK и поставить на телефон

Скачать: **https://194-87-252-181.sslip.io:4443/app** — там номер версии, APK и
как пройти предупреждение Play Protect. Прямая ссылка на файл —
`/app/vpn-<N>.apk` (отдаётся с `Range`, докачка не обрывается).
Android попросит разрешить установку из неизвестных
источников — это ожидаемо, приложение раздаётся в обход магазинов; если стоит
предыдущая версия, номер сборки растёт сам, и APK встанет поверх.

Для автоматической установки на подключённый по USB телефон есть скрипт:
`scripts/install-apk.sh` (по умолчанию берёт последнюю сборку из CI).

```bash
scripts/install-apk.sh
```

**Для скрипта нужен только `adb`** — JDK, Android SDK и Gradle не требуются.
`adb` берётся из `.tools/platform-tools/` (скачивается один раз вручную) или из
`PATH`. На телефоне надо включить отладку по USB.

**Что приложение делает сейчас:** запускается, поднимает туннель (см. раздел
«VPN РАБОТАЕТ» ниже) и входит через живой API. Главный экран показывает
«подключено / нет»; зелёного «защита подтверждена» нет намеренно — проба защиты
остаётся заглушкой, и выдавать её за успех нельзя (§6 архитектуры).


## VPN РАБОТАЕТ

Туннель поднимается по-настоящему. Проверено на эмуляторе:

```
event: name=CONNECTED ... via UDP on tun/10.84.0.42/
18: tun0: <POINTOPOINT,UP,LOWER_UP> mtu 1400
    inet 10.84.0.42/24 scope global tun0
8.8.8.8 dev tun0
```

Движок OpenVPN 3 лежит в APK как `libovpn3.so` для arm64-v8a и x86_64.
Скриншот: `docs/testing/2026-10-04-tunnel-connected.png`.

**Экран показывает «Защита не подтверждена» — и это правильный ответ.** Поднятый
интерфейс не доказывает, что трафик пошёл через него. Зелёный статус появится
только после реального замера (§6), а не от факта подключения.

### Как проверить локально

Локальная сборка занимает 15 секунд вместо 10 минут в CI:

```bash
cd android && JAVA_HOME="D:/VPN_app/.tools/jdk17" ./gradlew :app:assembleDebug --no-daemon
```

Профиль для теста кладётся в приватный каталог приложения (текст с приватным
ключом через намерение не передаётся):

```bash
adb push <профиль> /data/local/tmp/p.ovpn
adb shell "run-as com.impossi8le.vpnapp cp /data/local/tmp/p.ovpn files/profile.ovpn"
```

Логи ядра — `adb logcat -s VpnTunnel`. Там видно каждое событие и точную причину
отказа; без них видно только «туннель не поднялся».

## Локальный запуск на эмуляторе

Тулчейн есть локально: SDK в `.tools/sdk` (поставлен через `cmdline-tools`),
JDK — `.tools/jdk17` (Temurin 17). **JDK 21 из Android Studio (`D:\AndroidStudio\jbr`)
не подходит** — `jvmToolchain(17)` не находит 17-й тулчейн под 21-м.

```bash
scripts/run-emulator.sh
```

Скрипт создаёт AVD `vpnapp-api35` при отсутствии, поднимает эмулятор, ждёт
`sys.boot_completed` (а не только появления устройства — установка на ещё не
поднятую систему падает) и ставит последний APK из CI.

## Границы модулей

Стрелка = «зависит от». Нарушение направления — ошибка проектирования.

```
:app
 ├─ :feature:auth  :feature:home  :feature:configs  :feature:account
 │    └─ :core:domain, :core:ui
 ├─ :core:network  :core:config  :core:security  :core:tunnel  :core:protection
 │    └─ :core:domain
 └─ :vpnservice ─── :core:config + :vpnengine (OpenVPN 3, JNI)
```

`core:domain`, `core:config`, `core:network` — **чистый Kotlin/JVM**: тесты идут
без эмулятора. Остальные `core:*` — Android-библиотеки.

## Лицензия

**Здесь расхождение, которое надо закрыть решением владельца.** ics-openvpn
(единственный код под GPLv2) в проект **не вендорён**: каталога `android/vendor`
нет, `include(":vendor:ics-openvpn")` в `settings.gradle.kts` закомментирован.
Реально используются движки под слабым копилефтом и **ни один не заражает
приложение**:

| Компонент | Лицензия | Заражение |
|---|---|---|
| OpenVPN 3 (Android-движок) | MPL 2.0 | нет — файловое копилефто, не проектное |
| TunnelKit (iOS-стек) | GPLv3 **с исключением Apple App Store** (§7) | нет в рамках распространения |
| Наш код | — | решается лицензией репозитория |

Значит `LICENSE = GPLv2` в корне **не следует из кода**, а является отдельным
выбором (в архитектуре §0 он записан как «следствие выбора движка» — это было
верно для отклонённого пути с ics-openvpn). Сводить весь проект под GPLv2 никто
не обязан. Пока решение не принято, `LICENSE` и этот раздел остаются в
расхождении — оно честно отмечено, а не спрятано.

## Экраны

**Экранов (маршрутов) в коде — 10** (`AppDestination.kt`: Startup, Login,
LoginWaiting, Connection, Account, NoSubscription, AccessRevoked, HowToEnableVpn,
About, Demo). Один из них, Connection, покрывает восемь состояний
подключения. Число «восемнадцать» из `docs/design/mockup.html` описывает исходный
макет, который **помечен устаревшим** — актуальная спека того, что реализовано,
лежит в `docs/design/2026-10-06-implemented-ui-spec.md`.

**Вход → экраны дальше.** Настоящий вход ждёт подтверждения в Telegram, которого
в сборке для проверки нет. Поэтому на экране «Проверяем вход» есть кнопка
«Демонстрация: показать экраны дальше» — без неё десять экранов после входа
проверить нельзя. Она названа прямо и не выдаёт себя за состоявшийся вход.

Главный экран подключения — **один экран на восемь состояний**, а не восемь
маршрутов: они различаются текстом, цветом кольца и действием кнопки, но не
составом. Разводить их по маршрутам значило бы синхронизировать маршрут с
состоянием туннеля, а маршрут можно выставить неверно.

Проверено на эмуляторе: туннель поднимается (`tun0`, событие `CONNECTED`), а
экран показывает только «подключено / нет» и имя работающего подключения.
Блок «СОЕДИНЕНИЕ: не пройдено» снят с главного экрана 2026-10-06: проба защиты
всё ещё заглушка, и показывать её исход как факт нельзя — это тот же инвариант §6,
что и запрет на зелёный из системного флага. Актуальная спека UI —
`../docs/design/2026-10-06-implemented-ui-spec.md`.

Скриншоты: `docs/testing/`.

## Что нужно от бэкенда

Спецификация API: [`docs/api/`](../docs/api/).

| Документ | Что внутри |
|---|---|
| [Обзор](../docs/api/README.md) | Четыре эндпоинта, чего API не делает, три расхождения |
| [Контракт](../docs/architecture/2026-10-02-api-contract.md) | Протокол: методы, поля, коды ошибок |
| [Аудит](../docs/api/2026-10-05-contract-audit.md) | Сверка контракта с кодом |
| [Данные](../docs/api/2026-10-05-data-requirements.md) | Что нужно каждому экрану |

**Эндпоинтов ровно четыре:** `POST /auth/link`, `POST /auth/poll`, `GET /me`,
`GET /config/{id}`.

**Ключевое для бэкенда: статус защиты с сервера не отдаётся.** Он собирается на
устройстве из трёх измеренных фактов, и тип устроен так, что никакой ответ
сервера не может породить зелёный статус. Поле `"protected": true` было бы
непроверяемой ложью — и потому самой опасной: на её основе пользователь
перестаёт осторожничать.

**Сервер обязан присылать `error.code`.** Клиент различает три разные ситуации
по одному статусу `403` (`account_blocked`, `config_revoked`,
`subscription_expired`), поэтому голый статус без кода он считает неожиданным
ответом и показывает «не удалось» вместо понятной причины.

Пока сервер не готов, работает подставной бэкенд `MockApi`: три подключения,
одно истёкшее, вход с любым четырёхзначным кодом. Он **не имеет доступа к
вердикту защиты** — тест это проверяет явно.
