# Обновление приложения из самого приложения

Дата: 2026-10-05. Статус: **реализовано, юнит-тесты и сборка APK зелёные
локально**. Проверка на живом устройстве (баннер, скачивание, установка поверх)
и первый прогон CI с публикацией релиза — за человеком.

Прогон: `JAVA_HOME=D:/VPN_app/.tools/jdk17 ./gradlew test :app:assembleDebug`
— зелёный; из новых тестов `UpdateStatusTest` 24, `UpdateApiTest` 5,
`UpdateCheckerTest` 9, `ApkDownloaderTest` 4. Инструмент локальной сборки лежит в
репозитории (`.tools/jdk17`, `.tools/sdk`) — см. `scripts/local-build.md`.

**Проверено на телефоне 2026-10-06** (Galaxy S23): баннер «Доступна новая версия
1.0.93», скачивание 106 640 835 байт в кеш, системный установщик, установка
v92 → v93 поверх (подписи обоих релизов совпадают — `3c23f60a…`), новая иконка на
лончере. Отказ «Приложение не установлено» воспроизведён и объяснён: релизный APK
не ставится поверх отладочной сборки (подписи `752d91a1…` против `3c23f60a…`),
это свойство Android, а не дефект.

## Задача

Пользователь должен узнавать из приложения, что вышла новая версия, и обновляться,
не выходя из него. Сейчас узнать неоткуда: версия на экране «О сервисе»
захардкожена, о выходе новой сборки приложение не знает, а CI кладёт APK в
артефакт прогона, который анонимно скачать нельзя.

## Решения (утверждены)

| Вопрос | Решение |
|---|---|
| Источник данных о версии | **Публичный GitHub Release** репозитория `impossi8le/vpn-app-design` |
| Установка APK | **PackageInstaller внутри приложения**, системный диалог |
| Когда проверять | **При запуске + кнопка «Проверить обновления»** в «О сервисе» |
| Публикация релиза | **Добавить автопубликацию** в CI-workflow |

## Поведение

1. При запуске приложение асинхронно читает последний релиз и сравнивает
   `versionCode` сборки с номером из тега.
2. Если версия новее — на главном экране появляется закрываемый баннер
   «Доступна версия X», а в «О сервисе» — строка с кнопкой «Обновить».
3. Кнопка скачивает APK, показывает прогресс и открывает системный диалог
   установки.
4. Если GitHub недоступен или ответ не разобрался — приложение **честно
   сообщает «не удалось проверить обновления»** и не делает вид, что версия
   актуальна.

## Привязка к сборке git

Сейчас версия не привязана ни к чему: `AppRoot.kt:287` отдаёт захардкоженную
`"1.0.0"`, экран «О сервисе» показывает её. Это разрыв: `AndroidManifest` и CI
знают одно, интерфейс — другое.

Что делаем:

- Экран читает `BuildConfig.VERSION_NAME` и `BuildConfig.VERSION_CODE` — их
  заполняет AGP из `ANDROID_VERSION_NAME`/`ANDROID_VERSION_CODE`, которые CI уже
  выставляет (`1.0.<run_number>` и `run_number`).
- В `BuildConfig` добавляется поле `GIT_SHA` из `GITHUB_SHA`; в «О сервисе»
  показывается короткий (7 символов) SHA и дата коммита. Сборка, скачанная из
  релиза, теперь однозначно опознаётся.
- Тег релиза — `android-v<N>`, где `N` = `versionCode` = `github.run_number`.
  Тег и есть машинно-читаемая привязка: и к номеру сборки, и к коммиту в main.

## CI: публикация релиза

В `.github/workflows/android.yml` после успешного `test` в джобе `release`
(там уже есть подписанный APK и `REQUIRE_SIGNING`) добавляется шаг:

- создаётся GitHub Release с тегом `android-v${ANDROID_VERSION_CODE}` и именем
  `1.0.<run_number>`;
- APK прикладывается ассетом с именем `vpn-app-android-<N>.apk`;
- используется `GITHUB_TOKEN` (права `contents: write`), внешний PAT не нужен.

Релиз создаётся только на push в `main` — там же, где сейчас работает джоба
`release`. Пока секреты подписи не заданы, джоба пропускается и релиза нет; это
существующее поведение, его не меняем.

## Компоненты

### `core/domain` — правило сравнения версий

Чистая логика без Android, тестируется JUnit5 как остальной домен.

```kotlin
/** Разбор тега релиза в номер сборки. `null` — тег не наш или мусор. */
fun parseReleaseTag(tag: String): Int?          // "android-v12" → 12
/** Нужно ли обновление. Неизвестный номер — «не знаем», не «да». */
fun updateStatus(current: Int, latest: Int?): UpdateStatus
sealed interface UpdateStatus { object UpToDate; data class Available(val code: Int); object Unknown }
```

Разбор тега устойчив к мусору: `android-v12`, `v1.0.5`, `12`, пустая строка.
Тег не формата `android-v<N>` → `Unknown`, а не «обновление доступно».

### `core/network` — `UpdateApi`

`OkHttpClient` уже есть в `ApiClient` (таймауты 15/30/45 с). Обращается к
`https://api.github.com/repos/impossi8le/vpn-app-design/releases/latest`:

```kotlin
/** Сырые данные релиза. Номер сборки из тега извлекает домен, не сеть. */
data class ReleaseInfo(val tagName: String, val apkUrl: String)
sealed interface UpdateError { NetworkUnavailable; NotFound; RateLimited; Unexpected }
suspend fun latestRelease(): Result<ReleaseInfo>
```

Разделение осознанное: `UpdateApi` отдаёт то, что пришло (`tagName`), а
`parseReleaseTag` из `core/domain` решает, наш это тег или мусор. Так правило
разбора тестируется без сети и меняется в одном месте.

Обрабатываемые исходы GitHub:

| HTTP | Смысл | Поведение |
|---|---|---|
| 200 | есть релиз | ищем `.apk`-ассет; нет ассета → `Unexpected` |
| 404 | релизов нет | «обновлений не найдено», не ошибка |
| 403 | лимит анонимных запросов | «не удалось проверить», повтор позже |
| сеть | нет связи | «не удалось проверить» |

Тот же стиль, что в `ConfigApi`: `Result` + типизированная ошибка в домене.

### `AppGraph` — сборка зависимости

`UpdateApi` создаётся в графе рядом с `AuthApi`/`ConfigApi` и передаётся на
экран «О сервисе» и в источник баннера.

### UI

- **`AboutScreen`**: реальные версия/`GIT_SHA`, строка «Доступна версия X» и
  кнопка «Обновить» (кнопка «Проверить обновления», когда обновления нет).
- **Главный экран**: закрываемый баннер о доступном обновлении.
- **Скачивание**: поток в `cacheDir` с прогрессом; обрыв — повтор, частичный
  файл удаляется.
- **Установка**: `PackageInstaller` + `FileProvider` (`content://`, иначе
  Android 7+ бросит `FileUriExposedException`). Перед установкой проверяется
  `canRequestPackageInstalls()`; при запрете — ведём в
  `ACTION_MANAGE_UNKNOWN_APP_SOURCES`.

### Манифест

Добавляются `REQUEST_INSTALL_PACKAGES` и `<provider>` для `FileProvider`.
`INTERNET` уже есть.

## Что НЕ делаем

- Не трогаем бэкенд и его четыре эндпоинта — источник выбран внешний.
- Не проверяем подпись вручную: система сама отвергнет APK с чужим ключом,
  установка «поверх» просто не пройдёт.
- Никакого `latest.json`-манифеста: тег и есть версия.

## Принудительное обновление (добавлено 2026-10-06)

Когда сборка отстала настолько, что работать не может, приложение обязано
обновиться, а не предлагать это сделать. Экран блокируется целиком.

**Откуда порог.** Файл `min-supported.txt` в корне репозитория с одним числом.
Читается по `raw.githubusercontent` (анонимно, без лимита API). Поднять порог —
один коммит, видно в истории git, выпускать сборку не нужно.

**Отсутствие порога не блокирует.** Нет файла, нет сети, мусор в файле —
приложение работает как обычно. Обратное правило запирало бы человека вне
оплаченного клиента из-за неполученной цифры, что хуже устаревшей сборки.

**В отладочных сборках порог не применяется** (`enforceMinSupported = !DEBUG`):
`versionCode` debug-сборки равен 1, то есть ниже любого порога, и включённая
проверка заперла бы разработчика вне собственного приложения.

Блокирующий экран — `ForceUpdateScreen` в `feature:account`. Рисуется вместо
всей навигации: маршрут можно выставить неверно или уйти с него кнопкой «Назад»,
а сборка от этого не станет поддерживаемой. Есть кнопка «Я обновился — проверить
снова», чтобы обновившийся через бота не перезапускал приложение.

## Иконка приложения (добавлено 2026-10-06)

Раньше иконки не было вовсе: в манифесте отсутствовал `android:icon`, и система
рисовала стандартного робота. Теперь — adaptive icon (`mipmap-anydpi-v26`):
векторный щит в акценте `Ice #6FB3FF` на подложке `#12151B`. Тот же щит, что на
экране подключения, — иконка не вводит новый язык.

PNG не нужны: `minSdk 26` означает, что adaptive поддерживается везде, где
приложение вообще запускается. Рисунок вписан в центральные 54dp из 108dp —
запас под круглую и квадратную обрезку лончером.

## Тесты

- Разбор тега: `android-v12`→12, `v1.0.5`, `12`, мусор, пусто.
- Сравнение версий: новее, равно, старше, `Unknown`.
- `MockWebServer` на `UpdateApi`: 200 с ассетом, 200 без ассета, 404, 403, обрыв.
- Существующий гейт CI «выполнено N тестов, N > 0» накрывает новые
  автоматически — это уже работает и подделка его не пройдёт.

## Риски

| Риск | Тяжесть | Митигация |
|---|---|---|
| GitHub недоступен из РФ | высокая | Честное «не удалось проверить»; при систематических жалобах переносим источник на бэкенд — это смена одной реализации `UpdateApi`, интерфейс не меняется |
| Анонимный лимит GitHub API (60/час на IP) | низкая | Проверка при запуске + вручную, не в цикле; лимит недостижим |
| Пользователь отказывает в установке из неизвестного источника | средняя | Ведём инструкцией в настройки, как уже сделано для разрешения VPN |
| Ошибка в CI создаёт релиз без APK | низкая | Тест проверяет наличие ассета; отсутствие ассета — не «обновление» |
