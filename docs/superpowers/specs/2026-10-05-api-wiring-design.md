# Подключение реального API к Android-клиенту — дизайн

Дата: 2026-10-05. Статус: **реализовано** (см. прогон
[`../../testing/2026-10-05-api-wiring-live.md`](../../testing/2026-10-05-api-wiring-live.md)).

Исходные документы: [ответ бэкенда](../../api/2026-10-05-backend-response.md),
[ТЗ и расхождения](../../api/README.md),
[контракт](../../architecture/2026-10-02-api-contract.md).

> **Изменение 2026-10-06 — подача защиты на главном экране снята.** Спека
> проектировалась до того, как выяснилось, что проба защиты — заглушка: спека
> сохраняла §6 «не показывать зелёное», подразумевая, что экран будет говорить
> «проверяем» / «не проверено». Владелец решил иначе. Поскольку проба ничего не
> измеряет, экран теперь не говорит о защите **вообще**: ни «защищено», ни
> «проверка не прошла». Показываются ровно два честных факта из состояния
> туннеля — «Подключено» + имя работающего конфига, либо «Не подключено».
> Инвариант §6 в домене не тронут (типы и `ProtectionGate` на месте), но из UI
> он больше не виден. Подробности и обоснование — [`../../api/README.md`](../../api/README.md),
> раздел про защиту.

## 0. Что проверено перед проектированием

Живой бэкенд `https://194-87-252-181.sslip.io:4443/api/v1` отвечает по контракту
(проверено запросами 2026-10-05):

| Запрос | Ответ |
|---|---|
| `GET /health` | `200 {"status":"ok","service":"client-api"}` |
| `POST /auth/link` | `201` с `public_code`, `deep_link`, `expires_at` |
| `POST /auth/link` (хеш без `sha256:`) | `201` — префикс необязателен |
| `POST /auth/poll` (верный секрет, не подтверждено) | `200 {"status":"pending","retry_after_ms":2000}` |
| `POST /auth/poll` (неверный секрет) | `401 {"error":{"code":"invalid_secret"…}}` |
| `GET /me` без токена | `401 {"error":{"code":"unauthorized"…}}` |

Клиентский слой (`AuthApi`, `ConfigApi`, `ErrorMapping`) написан и покрыт тестами
против mock-сервера. **В работающем приложении он не подключён.**

## 1. Что не работает сейчас

> Раздел описывает состояние **до** реализации — это диагноз, ради которого
> написана спека. После подключения живого бэкенда (см. статус выше) всё
> перечисленное починено: вход, `/me`, загрузка `.ovpn`, туннель, выход.
> `MockApi` остался только в тестах и за debug-кнопкой демо-режима.

| Симптом | Причина |
|---|---|
| Вход не происходит | `AuthViewModel` не инстанцируется; `StartLogin` — `else -> Unit` в `MainActivity` |
| Список подключений — стубы | `MainActivity:147` зовёт `DemoMode.api` (`MockApi`) |
| Базы нет нигде | строки `sslip.io` нет ни в одном файле сборки |
| Профиль в туннель не идёт | `ConfigApi` не вызывается, `profile.ovpn` никто не пишет |
| Выход не гасит всё | `AppIntent.SignOut` не обрабатывается |

## 2. Решения (согласованы)

- **Объём:** весь сквозной путь — вход → `/me` → загрузка `.ovpn` → туннель.
- **Ввод кода:** поле 6 цифр прямо на экране «Проверяем вход».
- **Адрес:** одна константа в одном файле.
- **Демо-путь:** кнопка «показать экраны дальше» — только в debug; `MockApi` остаётся в тестах.
- **Профиль:** скачивается один раз, лежит на устройстве, переиспользуется без
  повторных запросов, удаляется по истечении срока.
- **Проверка:** вручную, с реальным подтверждением в боте.

## 3. Архитектура

### 3.1. `Backend.kt` — адрес

Новый файл в `:app`:

```kotlin
const val API_BASE_URL = "https://194-87-252-181.sslip.io:4443/api/v1"
```

Хост — валидный для TLS: сертификат Let's Encrypt выпущен на
`194-87-252-181.sslip.io`. Пиновать IP нельзя — строка sslip.io переживёт переезд
сервера, IP нет. Проверка TLS включена (цепочка валидна, `OkHttp` по умолчанию).

### 3.2. `AppGraph.kt` — точка сборки

Один объект собирает зависимости и повторяет порядок выхода из `AccountViewModel`:

```kotlin
class AppGraph(context: Context, tunnel: TunnelControlling) {
    val apiClient: ApiClient
    val authApi: AuthApi
    val configApi: ConfigApi
    val sessionStore: SessionStore
    val profileStore: ProfileStore
    val configManager: ConfigManager

    suspend fun signOut() { /* туннель → профиль → сессия → токен */ }
}
```

Собирается один раз в `MainActivity` (`remember`). DI-библиотеку не тянем: модулей
с состоянием мало, граф в двадцать строк виден целиком — это тот же аргумент,
что уже записан в комментарии `MainActivity`.

**Инвариант §6 не затрагивается.** `AppGraph` не имеет доступа к
`ProtectionVerdict` и не может породить зелёный: доказательство защиты
собирается единственным конструктором в `core:domain` из трёх измеренных фактов.

### 3.3. Состояние и сессия

- `apiClient.sessionToken` — общий для `AuthApi`/`ConfigApi`.
- При старте: если `sessionStore.load()` вернул неистёкшую сессию — токен
  восстанавливается, экран входа пропускается.

## 4. Поток входа

`LoginScreen.onLogin` → `AppIntent.StartLogin`:

1. `AuthApi.startLogin(Build.MODEL)` → `LoginChallenge` (`publicCode`, `secret`,
   `deepLink`, `expiresAtEpochSeconds`).
2. Открыть Telegram системным `Intent` на `deepLink`.
3. `LoginWaitingScreen`: **поле 6 цифр + «Подтвердить»**. Текст правится: бот
   пришлёт код, введите его здесь.
4. Ввод → `AuthViewModel.submitNonce` → `pollSession(publicCode, secret, nonce)`:
   цикл `Pending` с паузой сервера; `Confirmed` → `sessionStore.save` +
   `apiClient.sessionToken` + переход на `Connection`.
5. Обратный отсчёт — из `challenge.expiresAtEpochSeconds` (не хардкод `5:00`).
6. Ошибки: `nonce_mismatch` → код можно ввести заново (операция жива);
   `invalid_secret`/истёкшая операция → новый вход.

`device_name` = `Build.MODEL` — закрывает расхождение №3 из аудита.

## 5. Список подключений

`AppRootState.configs` наполняется `ConfigApi.listConfigs()` (`/me`) через
`ConfigsViewModel`, а не `DemoMode.api`. Список — живой, с реальными статусами и
сроками. Пустой список — валидный ответ, не ошибка.

## 6. Профиль: одноразовая загрузка и хранение

**Принцип (согласован):** профиль качается один раз, лежит на устройстве и
переиспользуется. `GET /config/{id}` повторяется только тогда, когда это
действительно нужно.

### 6.1. Мета рядом с профилем

`FileProfileStore` владеет файлами в `filesDir/`:

```
profile.ovpn      сам профиль (уже пишется)
profile.meta      JSON: { configId, version, endDateEpochSeconds }
```

Версия и срок не секреты, шифровать нечего; мета лежит вплотную к профилю, и
`profileStore.clear()` уносит её вместе с ним — одна операция очистки, нет
рассинхрона.

### 6.2. Когда трогаем сеть

| Условие | Действие |
|---|---|
| Профиля нет | `GET /config/{id}` |
| Профиль есть, `endDate > now` | **запрос не нужен** — поднимаем из файла |
| Пользователь сменил страну | `GET /config/{новый id}` |
| `endDate <= now` | удалить профиль, соединения не будет |

**Клиент не опрашивает сервер, чтобы узнать «нет ли версии новее».** Такого
запроса в дизайне нет намеренно: это ровно то, от чего уходим. Версия из меты
нужна только внутри уже случившегося запроса — если при смене страны
`ConfigManager` получит ту же версию, что уже лежит, запись пропускается
(`AlreadyCurrent`), и профиль не перезаписывается зря.

### 6.3. Удаление по истечении

Профиль перестаёт работать по сроку — держать его незачем:

- **при подключении:** `endDate <= now` → `profileStore.clear()` + экран
  «подписка истекла»; туннель не поднимается;
- **при ответе `/me`:** сохранённый `configId` отсутствует в `/me` или его
  `status != active` → профиль удаляется.

### 6.4. Подключение

`StatusAction.Connect`:

1. Если профиль есть и не истёк → сразу `tunnel.connect()` (читает
   `filesDir/profile.ovpn`, путь уже совпадает).
2. Иначе — `GET /me`, выбрать активное подключение, `ConfigManager.apply(id, version)`,
   затем `tunnel.connect()`.
3. `ConfigManager.apply` даёт `ApplyResult`: `AlreadyCurrent` — не ошибка;
   `FetchFailed(SubscriptionExpired | ConfigRevoked | NetworkUnavailable)` —
   каждый показывает своё сообщение.

### 6.5. Выход

`AppIntent.SignOut` → `AppGraph.signOut()`: туннель → профиль+мета → сессия →
`sessionToken = null`. Порядок обязателен: ядро не должно держать удаляемый
профиль; сессия не должна исчезнуть раньше поднятого соединения.

## 7. Демо-путь

- Кнопка «Демонстрация: показать экраны дальше» — **только в debug**
  (`BuildConfig.DEBUG`). В release её нет.
- `MockApi` остаётся в тестах. `DemoMode` перестаёт быть основным путём.
- Проверить, какое поле включает `BuildConfig` в `:app`, и включить при
  необходимости (как это уже сделано в `:vpnservice`).

## 8. Тестирование

- **Юнит (JVM):** логика меты (чтение/запись/истечение), `AppGraph.signOut`
  порядок вызовов, выбор «нужен ли запрос» — чистые функции, отдельными тестами.
- **Инструментальные (эмулятор):** прогон UI до поля ввода кода.
- **Ручная проверка:** реальный вход через бота, `/me`, загрузка конфига,
  поднятие туннеля. Автотест с реальным `device_nonce` невозможен — код
  приходит в Telegram.

## 9. Риски и границы

| Риск | Митигация |
|---|---|
| Утечка `verb 3` из профиля в logcat | уже закрыто `ProfileSanitizer`; не регрессировать |
| Проба защиты тавтологична | проба не входит в объём; §6 в домене не ослаблен. **2026-10-06:** подача защиты снята с экрана — проба остаётся заглушкой (`UnavailableProbe`), UI о защите не говорит |
| Истёкший профиль поднимет туннель | проверка `endDate` перед подключением (§6.3) |
| Демо-кнопка в релизе | гейт `BuildConfig.DEBUG` |

**Вне объёма:** `/config` по таймеру без пользователя, фоновая синхронизация,
покупка/продление (живёт в боте), эгресс-замер (§14 архитектуры).
