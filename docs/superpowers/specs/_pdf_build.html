iOS-приложение для VPN-сервиса
с продажей через Telegram

Дата: 30 сентября 2026   |   Статус: на ревью   |   Масштаб: ~1000 пользователей

1. Задача

Дать клиентам существующего Telegram-бота бесшовный iOS-клиент: человек покупает подписку в Telegram, а приложение само получает конфиг с нашего сервера и подключается по OpenVPN. Пользователь не скачивает файлы и не задумывается о настройке.

Масштаб: ~1000 пользователей.

2. Зафиксированные решения

ВопросРешение
ПротоколOpenVPN (существующая инфраструктура, конфиги проверены)
ПродажаТолько Telegram. Приложение ничего не продаёт
Канал доставкиTestFlight (публичная ссылка)
Аккаунт разработчикаЗарубежный Apple ID, физлицо, $99/год
АвторизацияВход через бота (deep link + polling)

Приложение не является VPN-сервисом по духу Guideline 5.4: оно не продаёт и не предоставляет VPN-услугу, а выступает клиентом для уже оплаченного стороннего доступа. Это осознанная позиция, снижающая риск 5.4, но не устраняющая его.

3. Что показало исследование

Ограничения, которые нельзя обойти технически

  1. TestFlight-сборки умирают каждые 90 дней. Безусловно, без продления. Когда сборка истекает, тестер теряет приложение целиком — вместе с логином и локальными данными.
  2. Apple Developer Program License Agreement запрещает брать плату с Beta Testers и использовать TestFlight для «continuous distribution... in attempt to circumvent App Store».
  3. Guideline 5.4 требует, чтобы VPN-приложения публиковались организацией, а не физлицом.

Что работает в нашу пользу

  • TestFlight доступен в РФ-сторе, смена региона и Apple ID не нужны.
  • Действующие РФ-провайдеры (NvoVPN, MosVPN, WAY VPN, «Дядя Ваня РФ») уже годами распространяются именно через TestFlight и подтверждают работоспособность канала.
  • Продажа вне приложения не требует IAP по Guideline 3.1.1, потому что приложение не даёт доступ к цифровому контенту — оно подключает уже приобретённую услугу.

Технический флаг (не блокер): с декабря 2025 ТСПУ блокирует OpenVPN, L2TP и WireGuard. Пользователь подтверждает, что его конфиги коннектятся у клиентов через OpenVPN Connect. Это значит, что либо блокировка не повсеместна, либо на серверах есть обфускация. Риск отложен, но должен отслеживаться: если начнутся массовые отвалы, спасёт не приложение, а смена протокола.

4. Энтайтлменты и ограничения аккаунта

com.apple.developer.networking.networkextension со значением packet-tunnel-provider — self-serve с 2016 года. Запрос к Apple не требуется, одобрение не нужно: capability включается в Xcode и в App ID на портале. Запрос формы нужен только для managed-типов (Hotspot Helper, NE app push), к нам не относится.

Тип аккаунта (физлицо или организация) на этом слое не влияет ни на что.

Понадобится также App Group для передачи конфига между приложением и расширением.

Personal VPN (com.apple.developer.networking.vpn.api) — отдельный вопрос, который решается при реализации. Он нужен для NEVPNManager, но для NEPacketTunnelProvider с кастомным протоколом обычно достаточно packet-tunnel-provider. Если на устройстве всплывёт ошибка saveToPreferences → Code 5 "permission denied", значит нужен и он.

Разделение ответственности

  • UI-процесс — показывает состояние и инициирует подключение. Не содержит логики туннеля.
  • Расширение (NEPacketTunnelProvider) — единственное место, где живёт VPN. Работает в отдельном системном процессе, поднимается даже когда приложение свёрнуто.
  • App Group — единственный канал передачи данных между ними. Конфиг кладётся в общий контейнер.
  • Бэкенд — выдаёт профиль только активным подписчикам. Не знает, как работает OpenVPN.

6. Потоки

6.1 Вход по deep link

Юзер в приложении → «Войти через Telegram»
  → приложение открывает t.me/<bot>?start=login_<одноразовый токен>
  → пользователь жмёт Start в Telegram (бот уже знает его chat_id)
  → бот кладёт: токен → chat_id, срок жизни 5 минут, одноразовый
  → приложение опрашивает /auth/poll каждые 2 сек
  → получает долгоживущий сессионный токен
  → сохраняет в Keychain

Токен одноразовый и короткоживущий: даже если перехвачен, повторно не сработает.

6.2 Покупка → доступ

Юзер покупает в боте → вебхук платёжки → бот продлевает подписку (срок = now + N)
  → приложение при следующем обновлении /me видит активную подписку
  → разблокируется кнопка подключения

Приложение про подписку не знает ничего до запроса к бэкенду. Логика доступа живёт в одном месте.

6.3 «Обновить профиль»

Кнопка → GET /config (сессионный токен)
  → бэкенд проверяет: подписка активна?
      нет → 403 + причина (истекла / не оплачена)
      да  → возвращает .ovpn со свежими серверами
  → приложение пишет конфиг в App Group
  → расширение подхватывает при следующем подключении

Это ключевой механизм, ради которого всё делается: ротация серверов не требует действий от пользователя.

6.4 Подключение

Кнопка Connect → сохранение NETunnelProviderManager (система один раз спрашивает разрешение) → расширение читает конфиг из App Group → поднимает туннель через TunnelKit.

7. Компоненты

iOS

  • SwiftUI-приложение: экран входа, статус подписки, кнопка Connect, кнопка «Обновить профиль».
  • Расширение NEPacketTunnelProvider.
  • TunnelKit / Partout — реализация протокола OpenVPN на Swift. Лицензия GPLv3 с дополнительным разрешением на распространение через App Store под MPL 2.0, что для нас подходит.
  • Хранилище: сессионный токен — в Keychain, конфиг — в общем контейнере App Group.

Бэкенд (FastAPI или Go + PostgreSQL)

Бот

Существующий, плюс: хендлер login_<token> в /start и выдача ссылки-подписки как резервный путь.

9. Что сознательно не делаем

  • Не продаём из приложения. Любая кнопка оплаты внутри приложения немедленно создаёт нарушение 3.1.1 и риск 5.4. Продажа остаётся в Telegram.
  • Не пишем свой OpenVPN-движок. TunnelKit решает эту задачу и уже используется в бою.
  • Не делаем собственный личный кабинет. Функции кабинета — это бот.
  • Не поддерживаем iOS ниже 15 на первом этапе.
  • Не мигрируем на VLESS сейчас. Протокол работает; миграция — отдельное решение при появлении проблем.

10. Открытые вопросы

  1. Обфускация OpenVPN. Если ТСПУ начнёт валить соединения, obfsproxy/scramble в OpenVPN слабее, чем Reality. Решение о миграции откладывается до первых массовых жалоб.
  2. Лимит устройств. Сейчас не определён. Нужен ли лимит на количество устройств на подписку?
  3. Продление. Что видит пользователь, когда подписка истекла и профиль не обновляется — решаем на этапе плана.

11. План работ

  1. Зарубежный Apple ID + Developer Program, регистрация App ID с энтайтлментами.
  2. Каркас приложения + расширение, туннель поднимается на статичном конфиге.
  3. Бэкенд: четыре эндпоинта.
  4. Вход через бота end-to-end.
  5. «Обновить профиль» + проверка ротации на живом сервере.
  6. Закрытое тестирование на своих, затем публичная ссылка.
  7. CI для автоматического релиза каждые 60 дней.

Шаги 1–2 можно вести параллельно с 3–4.
