# Логирование и отправка отчётов об ошибках: клиент и контракт API

Дата: 2026-10-13 (обновлено 2026-10-15). Статус: **на ревью**. Владелец темы:
этот документ.

Область: **только клиент и то, что он вызывает.** Серверную обработку,
хранение, MCP и разбор через LLM бэкенд реализует сам — здесь этого нет
намеренно.

---

## 1. Задача

Логи ядра сейчас пишутся только при `BuildConfig.DEBUG`
(`vpnservice/.../VpnTunnelService.kt:229`), поэтому в релизе причина сбоя
теряется полностью: у поддержки остаётся скриншот. Ядро при этом печатает точную
причину (`TUN Error: tun_prop_error: … failed`) — но она уходит в никуда.

Цель клиентской части: **накапливать логи всегда, но никуда не отправлять их без
нужды**, и уметь отправить осмысленный обезличенный пакет — автоматически
(метрики) или по кнопке (полные логи + конфиг).

## 2. Принятые решения

| # | Решение |
|---|---|
| 1 | **MOS** — действующий бэкенд (`194.87.252.181`). Эндпоинты добавляются в приложение FastAPI, **не в nginx** |
| 2 | **Гибрид, без тумблеров согласия.** Метрики — автоматически; полные логи — по кнопке |
| 3 | В авто-метрики входят `configId`, `configName`, `serverHostPort` |
| 4 | `.ovpn` уходит **обезличенным**: ключевые блоки вырезает клиент, ключ не покидает устройство |
| 5 | Обработка на бэкенде — за владельцем; клиент только вызывает и ожидает ответ |

## 3. Что уже есть (проверено по коду)

скраббера, обезличивания конфига и транспорта**.

## 4. Архитектура клиента

```
core:domain            (чистый Kotlin/JVM — тестируется без эмулятора)
  ├── LogScrubber        — вырезает секреты из строки лога
  ├── ConfigAnonymizer   — вырезает ключевые блоки из .ovpn
  ├── LogBuffer          — ring-buffer: 2000 строк или 256 КБ, что раньше
  ├── ReportModel        — что уходит: Metric vs FullReport (типы)
  └── ReportQueue        — очередь недоотправленного (порт)

core:network
  ├── TelemetryApi       — POST /api/v1/telemetry/events
  └── ReportApi          — POST /api/v1/report

vpnservice / core:tunnel
  └── логи ядра пишутся в LogBuffer, а не только в Log.d

app / feature:account
  ├── TelemetryWorker    — WorkManager, периодическая отправка метрик
  └── кнопка → ReportCollector → ReportApi
```

Правила:

- **`LogScrubber` и `ConfigAnonymizer` — чистые функции без Android.** Их
  доказывает тест JVM, а не «вроде вырезали» — тот же приём, что с
  `ProfileSanitizer`.
- **Скраббер стоит на входе в буфер, а не на выходе.** Секрет не должен попасть
  в память устройства вообще.
- **`ReportModel.Metric` физически не содержит полей секретов.** Тип ограничивает,
  «дописать поле» некуда — как в `DiagnosticsInput`.

## 5. Поток данных

### 5.1 Автоматический (метрики)

1. Приложение пишет события: `state_change`, `error` (код из `ApiError` /
   `EngineState.Failed`), `connect_attempt` (итог + длительность).
2. Событие проходит `LogScrubber`, кладётся в персистентную очередь
   (`ReportQueue`, файл в `filesDir`).
3. `TelemetryWorker` (`PeriodicWorkRequest`, минимум 15 мин) шлёт батч на
   `POST /api/v1/telemetry/events`.
4. Ограничения: `NetworkType.CONNECTED` + `setRequiresBatteryNotLow(true)`.
   `UNMETERED` **не** требуем — метрики мелкие, полезны и на мобильной сети.
5. Неудача → `Result.retry()` + экспоненциальный backoff. Очередь в файле
   переживает перезапуск.

### 5.2 По кнопке

1. Пользователь жмёт существующую кнопку «Отправить отчёт в поддержку».
2. `ReportCollector` собирает: текст `buildDiagnostics` + последние строки
   `LogBuffer` + обезличенный `.ovpn`.
3. `ConfigAnonymizer` вырезает `<key>`, `<tls-auth>`, `<tls-crypt>`, тела PEM.
   Остаются `remote`, `proto`, `cipher`/`data-ciphers`, `route*`,
   `redirect-gateway`, `verb`, `auth`, `tun-*`.
4. Уходит `POST /api/v1/report`. Прежняя дорожка в бот поддержки сохраняется.

**Логи буферизуются всегда, включая релиз.** Буфер (2000 строк / 256 КБ) в
памяти пользователю незаметен, а уходит только по кнопке или в составе метрик.
Это снимает главное препятствие: сейчас в релизе собирать нечего.

**Кнопка обязана быть честной.** Не удалось — «не отправлено, попробуем позже»,
а не «отправлено». Ложное подтверждение отправки — тот же класс ошибки, что
ложный зелёный статус.

## 6. Контракт API (то, что клиент вызывает)

Префикс `/api/v1`, `Authorization: Bearer <session token>`. Анонимный запрос —
`401`. Формат ошибки — существующий `{"error":{"code","message"}}`; **`code`
обязателен всегда**, клиент различает ситуации по нему, а не по HTTP-статусу.

### 6.1 `POST /api/v1/telemetry/events` — авто-метрики

Клиент шлёт батч. Каждое событие несёт `event_id` (UUID, генерирует клиент) —
для идемпотентности при повторе.

```json
{
  "app_version": 102,
  "platform": "android",
  "events": [
    {
      "event_id": "0f9c…",
      "type": "state_change",
      "ts": "2026-10-13T09:20:11Z",
      "state": "connected",
      "config_id": "…",
      "config_name": "…",
      "server": "185.…:1194",
      "duration_ms": 4210
    },
    { "event_id": "1a2b…", "type": "error", "ts": "…",
      "code": "tun_prop_error", "state": "failed" }
  ]
}
```

**Что клиент ожидает в ответ:** `204 No Content`. Больше клиенту от этого
эндпоинта ничего не нужно — это запись «в одну сторону».

**Поведение клиента при ответах:**

| Ответ | Что делает клиент |
|---|---|
| `204` | удаляет отправленные события из очереди |
| `401` | очищает очередь метрик и перестаёт слать до нового входа (токена нет) |
| `400`/`422` | **отбрасывает** батч: тело не принято, повтор бессмыслен |
| `429` | оставляет в очереди, повторяет по backoff |
| `5xx`, сеть | оставляет в очереди, повторяет по backoff |
| всё прочее | оставляет в очереди, повторяет с ограниченным числом попыток |

### 6.2 `POST /api/v1/report` — полный отчёт по кнопке

**Что клиент шлёт:** `multipart/form-data`.

| Часть | Содержимое | Тип |
|---|---|---|
| `report` | текст `buildDiagnostics` | `text/plain` |
| `logs` | последние строки `LogBuffer`, gzip | `application/gzip` |
| `config` | обезличенный `.ovpn`, gzip (может отсутствовать) | `application/gzip` |
| `meta` | версия, модель, состояние туннеля | `application/json` |

**Что клиент ожидает в ответ:** `{"report_id": "…"}` со статусом `201` — по нему
поддержка находит отчёт. Если бэкенду удобнее вернуть `200` или `204` — клиенту
достаточно считаться «отправлено»; `report_id` нужен только для показа
пользователю и для строки в боте поддержки.

**Поведение клиента:**

| Ответ | Что делает клиент |
|---|---|
| `201`/`200`/`204` | «Отчёт отправлен», копирует текст в буфер, предлагает бота |
| `401` | «Сессия истекла — войдите заново»; отчёт сохраняется локально |
| `413` | «Отчёт слишком большой»; предлагает вариант без логов |
| `429` | «Слишком часто, попробуйте позже»; отчёт сохраняется локально |
| `5xx`, сеть | «Не отправлено, попробуем позже»; отчёт в локальной очереди |

**Ни при каком ответе отчёт не теряется молча.** Неудача кладёт его в
`ReportQueue`, успех — удаляет.

### 6.3 Чего клиент НЕ отправляет никогда

- Приватный ключ, `tls-auth`/`tls-crypt`-ключи, тела PEM.
- Токен сессии и Telegram ID.
- Полный `.ovpn` — только обезличенный.

Клиентская гарантия: этих данных нет в теле запроса, потому что их нет в
`ReportModel`. Тест доказывает это поиском подстроки в сериализованном теле.

## 7. Серверный контракт — минимальный (за бэкендом)

Клиенту важно ровно это, остальное решает владелец:

1. `code` в ошибке присутствует всегда (иначе клиент покажет «неизвестная
   ошибка»).
2. `event_id` не создаёт дублей при повторной отправке.
3. `report_id` возвращается, если бэкенд хочет, чтобы клиент его показал.
4. Размер: `logs` и `config` после gzip — единицы-десятки КБ; если бэкенд
   ставит лимит, клиент его получает как `413` и предлагает урезанный отчёт.

## 8. Тестовый план

JVM, без эмулятора:
- `LogScrubber`: PEM-блок, static-key, `Bearer …`, токен сессии, `device_nonce` —
  вырезаны; обычная строка не изменена. Позитивный и негативный случай.
- `ConfigAnonymizer`: из боевой фикстуры
  (`core/config/src/test/resources/anonymized-production.ovpn`) остаётся
  `remote`/`cipher`/`route`; тело PEM **отсутствует** — проверка подстрокой.
- `LogBuffer`: лимит по строкам/байтам, вытеснение старого, скраббер на входе.
- `ReportModel`: в `Metric` нет полей секретов (проверка сигнатуры типа).
- Сериализованное тело метрик и отчёта не содержит ни одного секрета из фикстуры.

Инструментальные:
- Кнопка пишет файл и не падает без сети.
- `TelemetryWorker` без сети → `retry`; при появлении сети → отправляет.

## 9. Что НЕ делаем

- **Тумблер согласия** — решение владельца.
- **`device_id`.** Его нет и он не нужен: лимиты — по сессии и IP.
- **Сторонняя крашлитика** (Firebase/Sentry-облако): вынесла бы данные за MOS.
- **Вывод о защите из разбора.** Разбор — про причину сбоя, не про безопасность.

## 10. Открытые вопросы

1. `report_id` в ответе — нужен клиенту для показа или бэкенд обходится `204`.
2. Лимит размера отчёта на бэкенде (влияет на форму `413`).
3. Явная строка об отправке диагностики в «О сервисе» — решение владельца.
