# Контракт API: клиент ↔ бэкенд

Дата: 2026-10-02 (обновлено 2026-10-15)
Статус: **реализован на бэкенде и проверен вживую**. Клиентская сторона
фиксирует **что отправляет и что ожидает получить**; реализация —
`docs/api/2026-10-05-backend-response.md`.

Связанные документы: `2026-10-02-vpn-app-architecture.md`, `docs/superpowers/specs/2026-09-30-vpn-app-design.md` §8, `docs/superpowers/specs/2026-10-13-error-reporting-design.md`.

| Правило | Значение |

| Транспорт | HTTPS, TLS 1.2+ |
| Формат | JSON, UTF-8 (кроме `/report` — multipart, и `min-supported` — text/plain) |
| Base URL | `https://194-87-252-181.sslip.io:4443/api/v1` (домена нет, см. backend-response §0) |

## 1. POST /auth/link — начать вход

Приложение просит ссылку для входа через бота.

**Запрос:**

```json
{
  "public_code": "a7f3c9d2e1b4",
  "secret_hash": "sha256:9f2a...",   // hash секрета; сам секрет НИКОГДА не отправляется
  "device_name": "iPhone 15",
  "platform": "ios",
  "app_version": "1.0.0"
}
```

- `public_code` — генерируется приложением, попадает в deep link, виден в чате.
- `secret_hash` — SHA-256 от секрета, сгенерированного приложением. Секрет в открытом виде не покидает устройство.
- `device_name`, `platform`, `app_version` — для поддержки и диагностики.

**Ответ `201`:**

```json
{
  "public_code": "a7f3c9d2e1b4",
  "deep_link": "https://t.me/example_bot?start=login_a7f3c9d2e1b4",
  "expires_at": "2026-10-02T10:15:00Z"
}
```

**Ошибки:** `409 public_code_conflict` (редко, приложение повторяет с новым кодом), `429 rate_limited`.

## 2. POST /auth/poll — получить сессию

Приложение опрашивает статус операции, предъявляя **секрет**.

**Запрос:**

```json
{
  "public_code": "a7f3c9d2e1b4",
  "secret": "s3cr3t-…"
}
```

Проверка: `sha256(secret)` должен совпасть с `secret_hash` из `/auth/link`. Знание одного `public_code` (он виден в ссылке) сессию не даёт.

**Ответ `200` — подтверждено:**

```json
{
  "status": "confirmed",
  "session_token": "eyJhbGciOi…",
  "expires_at": "2026-11-02T10:00:00Z",
  "chat_id": 123456789
}
```

### 2.1 Защита от login-CSRF (обязательно)

**Атака:** злоумышленник сам вызывает `/auth/link`, получает свой `public_code` и секрет, формирует deep link и отправляет его жертве. Жертва подтверждает вход в боте, думая, что входит в свой аккаунт; бот привязывает `chat_id` жертвы к операции злоумышленника. Злоумышленник опрашивает `/auth/poll` со своим секретом и получает сессию **аккаунта жертвы**. Атомарность `pending → confirmed` и одноразовость здесь не помогают: законный владелец секрета — сам атакующий.

**Митигация — привязка подтверждения к устройству, инициировавшему вход:**

1. Бэкенд при `/auth/link` генерирует `device_nonce` (случайный, короткий, легко читаемый) и возвращает его **только в чат бота**, рядом с кнопкой подтверждения. **В приложение `device_nonce` из `/auth/link` не возвращается.**
2. Бот показывает пользователю `device_nonce` и требует подтвердить **именно этот код**.
3. Приложение, начавшее вход, знает `public_code`, но не знает `device_nonce`. Оно получает `device_nonce` только от пользователя, который прочитал его в боте, и отправляет его в `/auth/poll` вместе с секретом.
4. `/auth/poll` требует совпадения `device_nonce` И валидного секрета. Несовпадение → `403 nonce_mismatch`.

Атакующий не видит чат жертвы и потому не знает `device_nonce`, который бот показал жертве. Без него его poll отклоняется, даже имея верный секрет.

**Изменение запроса `/auth/poll`:**

```json
{
  "public_code": "a7f3c9d2e1b4",
  "secret": "s3cr3t-…",
  "device_nonce": "4821"       // пользователь ввёл его в приложении, прочитав в боте
}
```

`device_nonce` — не секрет и не заменяет секрет: он замыкает подтверждение на устройство, что инициировало вход.

**В UI это шаг «Введите код из Telegram»** между открытием бота и завершением входа (добавить в состав состояний входа на W5).

**Ответ `200` — ещё не подтверждено:**

```json
{ "status": "pending", "retry_after_ms": 2000 }
```

Другие значения `status`: `expired` (операция протухла — начать заново), `denied` (пользователь отказал в боте), `attempt_limit_exceeded`.

**Ошибки:** `401 invalid_secret`, `403 nonce_mismatch`, `404 operation_not_found`, `429 rate_limited`.

**Требование атомарности:** переход `pending → confirmed` происходит ровно один раз. Повторный `/auth/poll` с тем же секретом после `confirmed` возвращает `409 already_consumed` — украденный `public_code` не позволяет перехватить готовую сессию.

**Восстановление после `409 already_consumed` (потерянный ответ):** если клиент не получил `confirmed` (сеть оборвалась) и повтор получает `409`, клиент **не блокируется навсегда**: он показывает «Войти заново» и начинает новую операцию `/auth/link`. Отдельного эндпоинта повторной выдачи той же сессии нет — повторное использование токена опаснее, чем повторный вход.

**Ограничения:** не более N попыток на операцию; не более M операций с одного IP в час. Конкретные значения — на стороне бэкенда.

## 3. GET /me — список подключений

Единица списка — **подключение (конфиг)**, не страна. На одну страну может быть несколько конфигов.

**Запрос:** без тела, только `Authorization`.

**Ответ `200`:**

```json
{
  "chat_id": 123456789,
  "configs": [
    {
      "id": "nl-ams-1",
      "name": "Нидерланды · Амстердам",
      "location": { "country_code": "NL", "city": "Амстердам" },
      "start_date": "2026-09-01T00:00:00Z",
      "end_date": "2026-12-01T00:00:00Z",
      "status": "active"
    },
    {
      "id": "nl-rtm-1",
      "name": "Нидерланды · Роттердам",
      "location": { "country_code": "NL", "city": "Роттердам" },
      "start_date": "2026-05-01T00:00:00Z",
      "end_date": "2026-09-01T00:00:00Z",
      "status": "expired"
    }
  ]
}
```

`status` ∈ `active` | `expired` | `revoked` | `pending`.

**Инварианты для клиента:**

- Статус **у каждого** подключения свой. Один истёк — остальные работают, экран не блокируется.
- Пустой `configs` — валидный ответ, не ошибка. Состояние «подписок нет».
- **Призывов к покупке в ответе нет.** Клиент не рендерит «продлить»: поле отсутствует намеренно.

**Ошибки:** `401 unauthorized` (сессия истекла → экран входа), `403 account_blocked`.

## 4. GET /config/{id} — получить .ovpn

**Запрос:** путь с `id` подключения, `Authorization`.

**Ответ `200`:**

```
Content-Type: application/x-openvpn-profile
Content-Disposition: attachment; filename="nl-ams-1.ovpn"
X-Config-Version: 2026-10-02T09:00:00Z
X-Config-Hash: sha256:ab12...

<сырое содержимое .ovpn>
```

- Тело — сырой `.ovpn`, не JSON.
- `X-Config-Version` — версия для идемпотентности: если у клиента уже эта версия, запись можно пропустить.
- `X-Config-Hash` — для валидации после записи.

**Бэкенд обязан отдавать свежий конфиг только активным подпискам.** Для `expired`/`revoked` — ошибка, конфиг не выдаётся.

**Ошибки:**

| HTTP | code | Поведение клиента |
|---|---|---|
| `401` | `unauthorized` | экран входа |
| `403` | `config_revoked` | состояние «доступ отозван» |
| `402`/`403` | `subscription_expired` | состояние «подписка истекла», конфиг не трогаем |
| `404` | `config_not_found` | обновить `/me`, перерисовать список |
| `410` | `config_retired` | конфиг отозван на сервере, выбрать другой |

## 4.1 POST /telemetry/events — обезличенные метрики (автоматически)

Клиент шлёт батч событий работы туннеля. Вызывается **фоново** (`WorkManager`),
без участия пользователя. Требует токен сессии.

Полное описание клиентского поведения — `docs/superpowers/specs/2026-10-13-error-reporting-design.md` §6.1.

**Запрос:**

```json
{
  "app_version": 102,
  "platform": "android",
  "events": [
    {
      "event_id": "0f9c8a…",
      "type": "state_change",
      "ts": "2026-10-13T09:20:11Z",
      "state": "connected",
      "config_id": "…",
      "config_name": "…",
      "server": "185.…:1194",
      "duration_ms": 4210
    }
  ]
}
```

- `event_id` — UUID, генерирует клиент. Нужен **только** для идемпотентности:
  повторный батч не должен создавать дублей.
- `type` — `state_change` | `error` | `connect_attempt`.
- `code` (у `error`) — машинный код, как в остальном API.

**Ответ:** `204 No Content`. Клиенту от этого эндпоинта больше ничего не нужно —
это запись в одну сторону.

**Обработка ответов клиентом:**

| HTTP | Что делает клиент |
|---|---|
| `204` | удаляет отправленное из очереди |
| `401` | чистит очередь метрик, молчит до нового входа |
| `403` | **оставляет в очереди**, повторяет позже: контракт использует `403` и для временной блокировки аккаунта, события терять нельзя |
| `400`/`422` | отбрасывает батч — повтор бессмыслен |
| `429`/`5xx`/сеть | оставляет в очереди, повтор по экспоненциальному backoff |

## 4.2 POST /report — полный отчёт по кнопке

Отправляется **только по действию пользователя** («Отправить отчёт в
поддержку»). Содержит то, чего нет в метриках: логи ядра и обезличенный конфиг.

**Запрос:** `multipart/form-data`.

| Часть | Содержимое | Тип |
|---|---|---|
| `report` | текст диагностического отчёта | `text/plain` |
| `logs` | последние строки лога ядра, **сжато gzip** (файл `logs.txt.gz`) | `application/gzip` |
| `config` | обезличенный `.ovpn`, **сжато gzip** (файл `profile.ovpn.gz`); может отсутствовать | `application/gzip` |
| `meta` | `version_code`, `model`, `tunnel_state` | `application/json` |

Логи и профиль приходят **сжатыми**: это многострочный текст с повторами. Сервер распаковывает обе части; отсутствие части означает «её нет», а не «пустая».

**Конфиг обезличен на устройстве:** ключевые блоки (`<key>`, `<tls-auth>`,
`<tls-crypt>`, тела PEM) вырезаны **до** отправки. Приватный ключ не покидает
устройство ни в каком виде — это требование, а не оптимизация.

**Ответ:** `{"report_id": "…"}`, статус `201`.

**Обработка ответов клиентом:**

| HTTP | Что делает клиент |
|---|---|
| `201`/`200`/`204` | «Отчёт отправлен», текст копируется в буфер (чтобы пользователь мог дописать в чат) |
| `401` | «Сессия истекла — войдите заново»; текст кладётся в буфер и открывается бот поддержки — иначе донести отчёт нечем |
| `413` | «Отчёт слишком большой»; текст кладётся в буфер ДО сообщения — иначе «вставьте вручную» нечего вставлять; открывается бот поддержки | предлагает вариант без логов |
| `429` | «Слишком часто»; отчёт сохраняется локально |
| `5xx`/сеть | «Не отправлено, попробуем позже»; отчёт в локальной очереди |

**Ни при каком ответе отчёт не теряется молча.**

- **Что клиент НЕ отправляет никогда:** приватный ключ, `tls-auth`/`tls-crypt`
  ключи, тела PEM, токен сессии, Telegram ID, полный `.ovpn`.

> **Бэкенд (MOS, 2026-10-15).** Оба эндпоинта реализованы и проверены вживую.
> `/telemetry/events` отвечает `204` и дедуплицирует по `event_id`; `/report`
> отвечает `201` с `report_id`, распаковывает `logs`/`config` и режет отчёт
> сверх лимита как `413 report_too_large` (не теряя текст отчёта). Подробности
> форматов и адресов — `docs/api/2026-10-05-backend-response.md`.

## 4.3 Лента сборок приложения — обновление и порог

Раздача APK идёт **с нашего сервера**, а не с GitHub Releases. Эндпоинты без
авторизации: сборку нужно уметь скачать до входа.

| Метод | Путь | Ответ |
|---|---|---|
| `GET` | `/api/v1/app/latest?platform=android` | `{"version": 106, "apk_url": "https://…/app/vpn-106.apk"}` |
| `GET` | `/api/v1/app/min-supported` | `text/plain`, одно число — минимальный `versionCode` |
| `GET` | `/app` | HTML-страница установки (версия, шаги, кнопка) |
| `GET` | `/app/vpn-{version}.apk` | сам APK (поддерживает Range — докачка) |

Поведение:
- `version` — наибольший номер среди файлов `vpn-<N>.apk`; нет ни одной сборки
  → `404 release_not_found`.
- `min-supported` недоступен/битый → `404 min_supported_missing`. **Клиент
  трактует это как «порога нет»**: запирать пользователя из-за неполученной
  цифры нельзя.
- `apk_url` ведёт на наш же `/app/vpn-<N>.apk`; пиновать внешний хост не нужно.

## 4.4 Обходы РФ-сервисов

Подсети, чей трафик идёт **мимо туннеля**. Список — состояние на сервере,
клиент его читает и правит.

| Метод | Путь | Авторизация | Назначение |
|---|---|---|---|
| `GET` | `/api/v1/app/bypass-routes` | нет | текущий список |
| `GET` | `/api/v1/app/bypass-services` | нет | каталог РФ-сервисов для выбора |
| `POST` | `/api/v1/app/bypass/resolve` | да | цели (домены/IP/CIDR) → `/24`-подсети |
| `POST` | `/api/v1/app/bypass/set` | да | перезаписать список |

**`GET /bypass-routes`** → `{"routes": ["155.212.204.0/24", …], "entries": [{"cidr": "…", "label": "vk.com"}, …]}`.
Ключ `routes` — плоский список CIDR, сохранён без изменений для уже
установленных сборок. `entries` несёт ту же подсеть с необязательной подписью.
Пустой список — обходов нет.

**`POST /bypass/resolve`** — тело `{"targets": ["vk.com", "87.240.129.0/24"]}`
→ `{"routes": ["87.240.129.0/24", …]}`. Голый IPv4 без префикса трактуется как
`/24`. Ошибки: `400 bad_request`, `400 too_many_targets`, `400 invalid_target`.

**`POST /bypass/set`** — тело `{"entries": [{"cidr": "…", "label": "…"}]}` (или
старая форма `{"routes": ["…"]}`) → `{"ok": true, "count": N, "backup": "…"}`.
**Любая плохая запись — отказ целиком** (атомарно, со бэкапом прошлого файла).
Ошибки: `400 bad_request`, `400 too_many_routes`, `400 invalid_routes`,
`500 write_failed`.

**Защита от утечки:** префикс шире `/8` (`/0`…`/7`) отвергается — такой маршрут
завернул бы весь трафик мимо туннеля. Потолок списка — 200 маршрутов.

## 5. Клиентская обработка (что важно для тестов)

| Ответ | Действие клиента |
|---|---|
| `/config` вернул валидный `.ovpn` | `ProfileStore.stage` → валидация → `commit` (атомарно) |
| `/config` вернул невалидный `.ovpn` | `stage` отклоняет, старая версия остаётся |
| `X-Config-Hash` не совпал после записи | `rollback`, показать ошибку |
| `401` на любом запросе | `SessionStore.clear()`, экран входа |
| Сеть недоступна | отдаём последний сохранённый профиль, показываем «нет связи с сервером» |

**При выходе из аккаунта** клиент удаляет сессию и конфиг (+ `.bak`). Иначе следующая сессия подхватит профиль предыдущего пользователя.

## 6. Что клиент НЕ делает

- Не продаёт, не продлевает, не открывает оплату. Покупка — в Telegram.
- Не отправляет приватный ключ или токен никуда, кроме нашего бэкенда по HTTPS.
- Не ходит на внешние сервисы за реальным IP (см. архитектуру §6).

## 7. Открытые вопросы к бэкенду

1. **Лимит устройств** — один профиль на пользователя или на устройство? Влияет на то, инвалидирует ли новый вход старую сессию.
2. **`status` при истечении** — что видит пользователь, когда профиль перестаёт обновляться: `expired` или `revoked`?
3. **Серверная сверка с БД при коннекте** (`client-config-dir` / `auth-user-pass-verify` / management). Определяет, работает ли отзыв через дроп записи для самодостаточного конфига.
