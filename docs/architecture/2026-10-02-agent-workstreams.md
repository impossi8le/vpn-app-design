# Разбивка на потоки: параллельная мультиагентная разработка

Дата: 2026-10-02
Статус: на ревью
Назначение: разбить реализацию на независимые потоки так, чтобы агенты работали параллельно в изолированных worktree, не читая работу друг друга.

Связанные документы: `2026-10-02-vpn-app-architecture.md`, `2026-10-02-api-contract.md`.

## 1. Принцип разбиения

Поток независим, если:
1. Все его зависимости **уже зафиксированы протоколом** из `CoreDomain`.
2. Он не импортирует код другого потока — только протоколы.
3. У него свои тесты, зелёные без остальных потоков (через fakes).

**W0 пишет протоколы первым.** После W0 потоки W1…W5 идут параллельно. Это тот «бриллиант» в графе зависимостей: одна вершина сверху, широкий параллельный слой, слияние в конце.

```
        W0  Foundation (протоколы + TestSupport)
       / | \  |  \  \  \
     W1 W2 W3 W4 W5  W8        ← параллельный слой
      \  \  |  /  |  /
        W6 Extension          ← ждёт W2, W4
        W7 Mock backend       ← ждёт W3
        W9 Integration + device ← ждёт W6
```

## 2. Потоки

Каждый поток описан как контракт: цель, файлы, зависимости, ограничения, критерии приёмки, тесты.

### W0 — Foundation: протоколы и TestSupport

**Цель:** интерфейсы из §5 архитектуры и фейки для них. Блокирует всё.
**Создаёт:**
- `Packages/CoreDomain/Sources/**` — модели и протоколы
- `Packages/TestSupport/Sources/**` — `FakeAuthService`, `FakeConfigService`, `FakeProfileStore`, `FakeSessionStore`, `FakeTunnelControlling`, `FakeProtectionProbe`, JSON-фикстуры
- `Packages/TestSupportMockBackend/` — пустой таргет, объявленный заранее (наполняет W7)
**Зависимости:** нет
**Ограничения:** только Foundation. Ни байта I/O. Компилируется сам.
**Критерий приёмки:** `swift build` зелёный; все протоколы из §5 объявлены; `ConnectionStatus.protected` невозможно сконструировать иначе как через `ProtectionProbe`.
**Тесты:** компиляционные (протоколы существуют, фейки удовлетворяют им). Плюс `ConnectionStatusTests`: из `NEVPNStatus.connected` нельзя получить `.protected`.

### W1 — Auth flow (состояние входа, без HTTP)

**Цель:** поток входа как состояние и оркестрация — открыть бота, дождаться ввода кода, возобновить опрос при возврате из фона, завершить вход.
**Реализует:** `SessionStore`, `KeychainBackend`, ViewModel входа.
**НЕ реализует:** HTTP-часть `AuthService` — это W3. W1 тестирует свою логику против `FakeAuthService`.
**Файлы:** `CoreSecurity/`, `FeatureAuth/`
**Зависимости:** W0
**Ограничения:** не трогает `CoreNetwork/` (там HTTP-часть, владелец — W3). Не трогает туннель и конфиг. `deviceNonce` не проходит через `/auth/link`.
**Критерий приёмки:** состояние входа проходит шаги «ожидание подтверждения → ввод кода из Telegram → проверка → готово»; возврат из фона возобновляет незавершённую операцию; выход чистит сессию и конфиг.
**Тесты (против `FakeAuthService`):**
- Deep link формируется с корректным `public_code` и открывается.
- Ввод `deviceNonce` передаётся в `pollSession` — без него вход не завершается.
- Возврат из фона (`scenePhase`) возобновляет незавершённую операцию.
- Отсутствие Telegram на устройстве — обработанное состояние.
- Потерянная операция (например, бот вернул `expired`) → предложение начать заново, не тупик.
- `logout` очищает Keychain и (через контракт с W2) профиль.
- Секрет персистится для возобновления в Keychain, не на диск в открытом виде.

### W3 — Networking (клиент API)

**Цель:** реализация контракта `2026-10-02-api-contract.md`, включая **всю HTTP-часть `AuthService`**.
**Реализует:** `ConfigService`, `HTTPAuthService` (включая проверку `device_nonce`), маппинг ошибок.
**Файлы:** `CoreNetwork/`
**Зависимости:** W0
**Ограничения:** не трогает UI и туннель. Все ошибки маппятся в типизированные. `device_nonce` отправляется в `/auth/poll`.
**Критерий приёмки:** каждый эндпоинт контракта реализован; каждый код ошибки из таблиц §2–5 маппится; `nonce_mismatch` и `already_consumed` обрабатываются.
**Тесты:** через `URLProtocol`-заглушку на фикстурах из `TestSupport`, с **реальным декодированием в модели** (не сравнением строк):
- `/auth/link`, `/auth/poll` (pending/confirmed/expired/denied/nonce_mismatch/already_consumed).
- `/me` декодируется в `[Connection]`; пустой `configs` — валидный ответ, не ошибка.
- `/config/{id}` — сырое тело; все коды `401/402/403/404/410`.
- `X-Config-Hash` проверяется после получения.

**Владение `AuthService` разделено:** W3 владеет HTTP-реализацией, W1 — потоком/состоянием. Протокол в W0 один; реализацию даёт W3; W1 зависит только от протокола. Это снимает скрытую связку W1↔W3, найденную на ревью.

### W2 — ConfigStore (атомарная запись .ovpn)

**Цель:** хранение профиля по протоколу §7 архитектуры.
**Реализует:** `ProfileStore`.
**Файлы:** `CoreConfig/`
**Зависимости:** W0
**Ограничения:** App Group контейнер. Никакой логики туннеля.
**Критерий приёмки:** `stage → commit` атомарен; `rollback` возвращает рабочую версию; невалидный `.ovpn` не доходит до `commit`.
**Тесты:**
- `stage` отклоняет битый профиль, старый остаётся нетронутым.
- Обрыв на середине `commit` → `.ovpn` валиден (старый или новый), никогда не полузаписан.
- `rollback` возвращает `.bak`.
- Расширение читает только `profile.ovpn`, никогда `.tmp`.
- `logout` удаляет `.ovpn` и `.bak`.

### W4 — TunnelKit verification

**Цель:** снять главный технический риск — совместимость архивного TunnelKit с реальными профилями **и с тулчейном** (собирается ли архивный пакет и линкуется ли в NE-таргет под текущим Xcode/Swift).
**Реализует:** `TunnelKitCore` (парсинг и построение конфигурации; поднятие туннеля — на W6).
**Файлы:** `Packages/TunnelKitCore/`
**Зависимости:** W0
**Ограничения:** TunnelKit пинится на коммите, вендорится. Версия не меняется без записи в спеку. Ядро **не импортирует `NetworkExtension`** — иначе не соберётся в тестах без устройства.
**Критерий приёмки:** архивный TunnelKit собирается и **линкуется в NE-таргет**; все реальные продакшен-`.ovpn` парсятся; конфигурация соответствует §8.3 спеки.
**Тесты:**
- **Build/link: NE-таргет с TunnelKit собирается** — это и есть реальный риск архивации, а не только парсинг.
- Парсинг реальных `.ovpn` — чистая функция, без устройства.
- IPv6 закрыт: маршрут по умолчанию не содержит IPv6 в обход.
- DNS уходит в туннель.
- Kill switch (`includeAllNetworks`) настроен.
- Директива, которую TunnelKit не понимает, — явная ошибка, не молчаливый пропуск.

### W5 — UI states (21 экран)

**Цель:** все состояния из макета, с ViewModel, тестируемыми без UI.
**Файлы:** `CoreUI/`, `FeatureHome/`, `FeatureConfigs/`, `FeatureAccount/`
**Зависимости:** W0
**Ограничения:** ViewModel зависит только от протоколов `CoreDomain`. Токены — из спеки §9, не выдумывать. Красный — только реальная опасность, янтарный — только процесс подключения.
**Критерий приёмки:** все 21 состояние из макета рендерятся; матрица главной кнопки из спеки §8.5 соблюдена.
**Тесты (не XCUITest, а ViewModel):**
- Матрица «состояние → текст и заливка кнопки» для всех строк.
- Зелёный рендерится только на `.protected`; на `.verifyingProtection` — «не проверено».
- **Обрыв туннеля → `.disconnected`**, кнопка возвращается в «Подключить» (регрессия раунда 1 макета: застревание с «Отключить»).
- **Провал замера на обрыве** — показывается третий исход, не вечное «проверяем».
- **Окно без защиты при смене подключения** — красный, предупреждение, подтверждение.
- **Эскалация ожидания 10/20/30 сек** — тексты сменяются по шагам.
- **Выбранное подключение сохраняется** между запусками.
- **Демо-режим** (блокер раунда 2: ревьюер Apple без подписки) — доступен, состояние достижимо.
- Отказ в разрешении VPN — не тупик.
- Один конфиг истёк — остальные работают.
- Пустой список — состояние «подписок нет».

### W6 — Extension (NEPacketTunnelProvider)

**Цель:** расширение, читающее профиль и поднимающее туннель.
**Файлы:** `VpnTunnelExtension/`
**Зависимости:** W2 (чтение профиля), W4 (`TunnelKitCore`)
**Ограничения:** вся логика парсинга — в `TunnelKitCore`, дублирования нет. Менеджер не создаёт (это app-side `TunnelManager`).
**Критерий приёмки:** расширение поднимает туннель на профиле из App Group. Отображение `NEVPNStatus → .verifyingProtection` — зона W9 (app-процесс), а не W6.
**Тесты:** юнит на границе «чтение из App Group → конфигурация»; отсутствие `NETunnelProviderManager` в таргете расширения; реальное поднятие — W9.

### W7 — Mock backend + контракт

**Цель:** исполняемая спецификация контракта для интеграционных тестов.
**Файлы:** `Packages/TestSupportMockBackend/` — **отдельный пакет, объявленный в W0, чтобы не править W0-пакет.**
**Зависимости:** W3 (согласование моделей), API-контракт
**Ограничения:** только для тестов, в продукт не попадает.
**Критерий приёмки:** мок воспроизводит все сценарии: вход (включая `device_nonce` и `nonce_mismatch`), истечение, отзыв, пустой список, все коды ошибок.
**Тесты:** сам мок покрыт тестами на соответствие контракту — иначе тесты на нём ничего не доказывают. Интеграционные тесты поверх мока владеет **W9**, не W7.

### W8 — CI и 60-дневный авто-релиз

**Цель:** сборка перестаёт работать через 90 дней — это гарантированный риск (спека §11).
**Файлы:** `.github/workflows/`, `fastlane/`
**Зависимости:** для прогона тестов — нет; для сборки/подписи нужен app-таргет этапа 1 (Apple ID, App ID, энтайтлменты).
**Критерий приёмки:** CI гоняет тесты на PR; fastlane умеет собрать и загрузить сборку.
**Тесты:** прогон CI на пустом PR; dry-run fastlane.

### W9 — Integration + device

**Цель:** слияние, app-side `TunnelManager`, проверка на реальном устройстве.
**Зависимости:** W6, W7, всё остальное
**Критерий приёмки:** чеклист спеки §14 этап 3 пройден: смена Wi-Fi/мобильной сети, сон, блокировка экрана, перезагрузка, отсутствие интернета, длительное подключение.
**Тесты:** интеграционные поверх `TestSupportMockBackend`; XCUITest на 21 состояние; **пробу защиты — на реальном устройстве** (симулятор туннели не поднимает), честность пробы тип не гарантирует; ручной чеклист.

## 3. Правила для агента потока

Каждый агент получает самодостаточный промпт (§4) и следует:

1. **Тест первым.** Падающий тест → минимальная реализация → рефактор. Использовать скилл `test-driven-development`.
2. **Не выходить за границы потока.** Не менять чужие модули. Не добавлять зависимости без записи в спеку. Не рефакторить несвязанное.
3. **Протоколы W0 заморожены версионно.** Механика (заменяет прежнее «не менять вообще», которое провалилось на первом же артефакте):
   - Протоколы помечены версией `W0-v1`. Внутри версии **запрещена правка сигнатур на месте**.
   - **Аддитивное изменение** (новый протокол, новый метод с дефолтом через `extension`, новое поле) — не ломает потребителей, вносится новой задачей поверх, без остановки потоков.
   - **Ломающее изменение** (сигнатура, семантика) — блокер: агент останавливается, поднимает письменную поправку к `architecture §5`, версия становится `W0-v2`, и только тогда потоки продолжают. «Обновлю спеку при мерже» запрещено — это то, на чём сломался прежний механизм.
4. **Работать в изолированном worktree** (`using-git-worktrees`), чтобы параллельные агенты не конфликтовали.
5. **Гейт:** перед сдачей — `swift build` и `swift test` зелёные, критерий приёмки выполнен, тесты покрывают перечисленные кейсы.
6. **Никаких секретов в логах.** Приватные ключи, токены, полный `.ovpn` — никогда.

## 5. Порядок запуска

| Слой | Потоки | Условие старта |
|---|---|---|
| 0 | W0 | сразу |
| 1 | W1, W2, W3, W4, W5, W8 | W0 смержен — **параллельно** |
| 2 | W6 (W2+W4), W7 (W3) | нужный поток слоя 1 смержен |
| 3 | W9 (все) | все смержены |

**Оценка параллелизма:** на слое 1 одновременно работают до 6 агентов в отдельных worktree. W4 — единственный поток с возможным отрицательным исходом (TunnelKit не собирается или несовместим); запускать первым в слое, потому что от его исхода зависит, имеет ли смысл остальное.

**Канонический layout путей** (ранее расходился между документами, приведён к одному):

```
Packages/
  CoreDomain/            W0
  TestSupport/           W0
  TestSupportMockBackend/ W0 (пустой) → W7
  CoreNetwork/           W3
  CoreConfig/            W2
  CoreSecurity/          W1
  TunnelKitCore/         W4
  CoreUI/                W5
Apps/
  VpnApp/                W9 (composition root, TunnelManager)
  VpnTunnelExtension/    W6
  Features/
    FeatureAuth/         W1
    FeatureHome/         W5
    FeatureConfigs/      W5
    FeatureAccount/      W5
```
