# Разбивка на потоки: параллельная мультиагентная разработка

Дата: 2026-10-02
Статус: на ревью
Назначение: разбить реализацию на независимые потоки так, чтобы агенты работали параллельно в изолированных worktree, не читая работу друг друга.

Связанные документы: `2026-10-02-vpn-app-architecture.md`, `2026-10-02-api-contract.md`.

## 1. Принцип разбиения

Поток независим, если:
1. Все его зависимости **уже зафиксированы протоколом** из `CoreDomain`.
2. Он не импортирует код другого потока — только протоколы.
3. У него свои тесты, зелёные без остальных потоков (через fakes).

**W0 пишет протоколы первым.** После W0 потоки W1…W5 идут параллельно. Это тот «бриллиант» в графе зависимостей: одна вершина сверху, широкий параллельный слой, слияние в конце.

```
        W0  Foundation (протоколы + TestSupport)
       / | \  |  \  \  \
     W1 W2 W3 W4 W5  W8        ← параллельный слой
      \  \  |  /  |  /
        W6 Extension          ← ждёт W2, W4
        W7 Mock backend       ← ждёт W3
        W9 Integration + device ← ждёт W6
```

## 2. Потоки

Каждый поток описан как контракт: цель, файлы, зависимости, ограничения, критерии приёмки, тесты.

### W0 — Foundation: протоколы и TestSupport

**Цель:** интерфейсы из §5 архитектуры и фейки для них. Блокирует всё.
**Создаёт:**
- `SwiftPackages/CoreDomain/Sources/**` — модели и протоколы
- `SwiftPackages/TestSupport/Sources/**` — `FakeAuthService`, `FakeConfigService`, `FakeProfileStore`, `FakeSessionStore`, `FakeTunnelControlling`, `FakeProtectionProbe`, JSON-фикстуры
**Зависимости:** нет
**Ограничения:** только Foundation. Ни байта I/O. Компилируется сам.
**Критерий приёмки:** `swift build` зелёный; все протоколы из §5 объявлены; `ConnectionStatus.protected` невозможно сконструировать иначе как через `ProtectionProbe`.
**Тесты:** компиляционные (протоколы существуют, фейки удовлетворяют им). Плюс `ConnectionStatusTests`: из `NEVPNStatus.connected` нельзя получить `.protected`.

### W1 — Auth (вход через deep link + polling)

**Цель:** флоу входа целиком, начиная от нажатия «Войти через Telegram».
**Реализует:** `AuthService`, `SessionStore`, `KeychainBackend`.
**Файлы:** `CoreNetwork/Auth/`, `CoreSecurity/`, `FeatureAuth/`
**Зависимости:** W0
**Ограничения:** не трогает туннель и конфиг. Секрет не проходит через Telegram (см. API-контракт §1–2).
**Критерий приёмки:** вход завершается при подтверждении в боте; возврат из фона возобновляет опрос; выход чистит сессию и конфиг.
**Тесты:**
- Deep link открывается с корректным `public_code`.
- `pollSession` предъявляет секрет, не `publicCode`.
- Повторный poll после `confirmed` → `already_consumed`, сессия не перехватывается.
- Возврат из фона (`scenePhase`) возобновляет незавершённую операцию.
- Отсутствие Telegram на устройстве — обработанное состояние.
- `logout` очищает Keychain.

### W2 — ConfigStore (атомарная запись .ovpn)

**Цель:** хранение профиля по протоколу §7 архитектуры.
**Реализует:** `ProfileStore`.
**Файлы:** `CoreConfig/`
**Зависимости:** W0
**Ограничения:** App Group контейнер. Никакой логики туннеля.
**Критерий приёмки:** `stage → commit` атомарен; `rollback` возвращает рабочую версию; невалидный `.ovpn` не доходит до `commit`.
**Тесты:**
- `stage` отклоняет битый профиль, старый остаётся нетронутым.
- Обрыв на середине `commit` → `.ovpn` валиден (старый или новый), никогда не полузаписан.
- `rollback` возвращает `.bak`.
- Расширение читает только `profile.ovpn`, никогда `.tmp`.
- `logout` удаляет `.ovpn` и `.bak`.

### W3 — Networking (клиент API)

**Цель:** реализация контракта `2026-10-02-api-contract.md`.
**Реализует:** `ConfigService` и HTTP-часть `AuthService`.
**Файлы:** `CoreNetwork/`
**Зависимости:** W0
**Ограничения:** не трогает UI и туннель. Все ошибки маппятся в типизированные.
**Критерий приёмки:** каждый эндпоинт контракта реализован; каждый код ошибки из таблиц §4–5 маппится.
**Тесты:** через `URLProtocol`-заглушку на фикстурах из `TestSupport`:
- `/auth/link`, `/auth/poll` (pending/confirmed/expired/denied).
- `/me` с пустым `configs` — не ошибка.
- `/config/{id}` — все коды `401/402/403/404/410`.
- `X-Config-Hash` проверяется после получения.

### W4 — TunnelKit verification

**Цель:** снять главный технический риск — совместимость архивного TunnelKit с реальными профилями.
**Реализует:** `TunnelKitAdapter` (парсинг и построение конфигурации; управление туннелем — заглушка до W6).
**Файлы:** `TunnelKitAdapter/`
**Зависимости:** W0
**Ограничения:** TunnelKit пинится на коммите, вендорится. Не менять версию без записи в спеку.
**Критерий приёмки:** все реальные продакшен-`.ovpn` парсятся; конфигурация туннеля соответствует требованиям §8.3 спеки.
**Тесты:**
- Парсинг реальных `.ovpn` — чистая функция, без устройства.
- IPv6 закрыт: маршрут по умолчанию не содержит IPv6 в обход.
- DNS уходит в туннель.
- Kill switch (`includeAllNetworks`) настроен.
- Директива, которую TunnelKit не понимает, — явная ошибка, не молчаливый пропуск.

### W5 — UI states (21 экран)

**Цель:** все состояния из макета, с ViewModel, тестируемыми без UI.
**Файлы:** `CoreUI/`, `FeatureHome/`, `FeatureConfigs/`, `FeatureAccount/`
**Зависимости:** W0
**Ограничения:** ViewModel зависит только от протоколов `CoreDomain`. Токены — из спеки §9, не выдумывать. Красный — только реальная опасность, янтарный — только процесс подключения.
**Критерий приёмки:** все 21 состояние из макета рендерятся; матрица главной кнопки из спеки §8.5 соблюдена.
**Тесты (не XCUITest, а ViewModel):**
- Матрица «состояние → текст и заливка кнопки» для всех строк.
- Зелёный рендерится только на `.protected`.
- Отказ в разрешении VPN — не тупик.
- Один конфиг истёк — остальные работают.
- Пустой список — состояние «подписок нет».

### W6 — Extension (NEPacketTunnelProvider)

**Цель:** расширение, читающее профиль и поднимающее туннель.
**Файлы:** `VpnTunnelExtension/`
**Зависимости:** W2 (чтение профиля), W4 (адаптер)
**Ограничения:** вся логика парсинга — в адаптере, дублирования нет.
**Критерий приёмки:** расширение поднимает туннель на профиле из App Group; `NEVPNStatus.connected` приходит в app-процесс и маппится в `.verifyingProtection`.
**Тесты:** юнит на границе «чтение из App Group → конфигурация»; реальное поднятие — W9.

### W7 — Mock backend + контракт

**Цель:** исполняемая спецификация контракта для интеграционных тестов.
**Файлы:** `TestSupport/MockBackend/`
**Зависимости:** W3 (согласование моделей), API-контракт
**Ограничения:** только для тестов, в продукт не попадает.
**Критерий приёмки:** мок воспроизводит все сценарии: вход, истечение, отзыв, пустой список, все коды ошибок.
**Тесты:** сам мок покрыт тестами на соответствие контракту — иначе тесты на нём ничего не доказывают.

### W8 — CI и 60-дневный авто-релиз

**Цель:** сборка перестаёт работать через 90 дней — это гарантированный риск (спека §11).
**Файлы:** `.github/workflows/`, `fastlane/`
**Зависимости:** нет (можно начинать сразу)
**Критерий приёмки:** CI гоняет тесты на PR; fastlane умеет собрать и загрузить сборку.
**Тесты:** прогон CI на пустом PR; dry-run fastlane.

### W9 — Integration + device

**Цель:** слияние и проверка на реальном устройстве.
**Зависимости:** W6, W9 ждёт всё
**Критерий приёмки:** чеклист спеки §14 этап 3 пройден: смена Wi-Fi/мобильной сети, сон, блокировка экрана, перезагрузка, отсутствие интернета, длительное подключение.
**Тесты:** XCUITest на 21 состояние + ручной чеклист на устройстве.

## 3. Правила для агента потока

Каждый агент получает самодостаточный промпт (§4) и следует:

1. **Тест первым.** Падающий тест → минимальная реализация → рефактор. Использовать скилл `test-driven-development`.
2. **Не выходить за границы потока.** Не менять чужие модули. Не добавлять зависимости без записи в спеку. Не рефакторить несвязанное.
3. **Не менять протоколы W0.** Если протокол оказался неверен — остановиться и поднять это как блокер, а не править молча: протокол общий для всех потоков.
4. **Работать в изолированном worktree** (`using-git-worktrees`), чтобы параллельные агенты не конфликтовали.
5. **Гейт:** перед сдачей — `swift build` и `swift test` зелёные, критерий приёмки выполнен, тесты покрывают перечисленные кейсы.
6. **Никаких секретов в логах.** Приватные ключи, токены, полный `.ovpn` — никогда.

## 4. Шаблон промпта потока

```
РОЛЬ: реализовать поток <Wn> — <название>.

ЧИТАТЬ СНАЧАЛА:
- docs/architecture/2026-10-02-vpn-app-architecture.md (§4, §5 для протоколов)
- docs/architecture/2026-10-02-api-contract.md (для W1, W3, W7)
- docs/superpowers/specs/2026-09-30-vpn-app-design.md (§8 для W5, §11 для W8)

ЦЕЛЬ: <одно предложение>

ЗАВИСИМОСТИ: W0 смержен. Протоколы из CoreDomain заморожены — не менять.

ФАЙЛЫ: <список>

ОГРАНИЧЕНИЯ:
- Только протоколы CoreDomain, без импорта кода других потоков.
- Тесты первыми. <специфичные ограничения потока>

КРИТЕРИЙ ПРИЁМКИ: <из §2>

ОБЯЗАТЕЛЬНЫЕ ТЕСТЫ: <список из §2>

ГЕЙТ ПЕРЕД СДАЧЕЙ: swift build + swift test зелёные; покрыты все перечисленные тесты;
не тронуты чужие модули; протоколы W0 не изменены (иначе — блокер, не правка).
```

## 5. Порядок запуска

| Слой | Потоки | Условие старта |
|---|---|---|
| 0 | W0 | сразу |
| 1 | W1, W2, W3, W4, W5, W8 | W0 смержен — **параллельно** |
| 2 | W6 (W2+W4), W7 (W3) | нужный поток слоя 1 смержен |
| 3 | W9 | все смержены |

**Оценка параллелизма:** на слое 1 одновременно работают до 6 агентов в отдельных worktree. W4 — единственный поток, который может дать отрицательный результат (TunnelKit несовместим); его стоит запустить первым в слое, потому что от его исхода зависит, имеет ли смысл остальное.
