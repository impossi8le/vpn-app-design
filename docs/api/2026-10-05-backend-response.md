# Ответ бэкенда: API реализован, как подключаться

Дата: 2026-10-05. Статус: **реализовано и проверено вживую**.
Отвечает на [README.md](README.md) и [аудит контракта](2026-10-05-contract-audit.md).

## 0. Как подключиться (домена нет)

Домена у сервиса нет и не будет. TLS обязателен, поэтому адрес берётся через
**sslip.io** — публичный DNS, который отдаёт IP прямо в имени хоста. Сертификат
Let's Encrypt уже выпущен и продлевается автоматически.

| Параметр | Значение |
|---|---|
| Base URL | `https://194-87-252-181.sslip.io:4443/api/v1` |
| Порт | `4443` (TLS) |
| Сертификат | Let's Encrypt, CN `194-87-252-181.sslip.io`, действителен до 12.12.2026 |
| Проверка TLS | **включена** (цепочка валидна, отключать не нужно) |

Формула хоста: `<IP с точками, заменёнными на дефисы>.sslip.io`. Резолвится
в `194.87.252.181` без собственного домена.

> Если сборка клиента требует «домен», а не IP, `194-87-252-181.sslip.io`
> — это и есть валидный хостнейм для TLS. Пиновать IP в приложении нельзя:
> при переезде сервера он поменяется, а строка sslip.io — нет.

Клиентские таймауты из `ApiClient.kt` (connect 15 с / read 30 с / call 45 с)
сервер укладывает: обычный ответ < 1 с, `/config/{id}` — до ~3 с (свежий
профиль тянется с VPN-ноды и кладётся в одноразовую ссылку).

## 2. Поток входа — как в контракте, плюс код из бота

Реализована защита от login-CSRF (§2.1 контракта) целиком:

1. Приложение само генерирует `public_code` и секрет, шлёт их в `/auth/link`.
2. **Бэкенд возвращает `deep_link`**, а `device_nonce` (6 цифр) генерирует и
   отдаёт **только в чат бота** рядом с подтверждением. В ответ API он **не
   попадает** — это и есть защита: укравший ссылку не видит чужой чат.
3. Пользователь открывает бота по `deep_link` (`t.me/free1vpnbot?start=login_<code>`),
   бот показывает код и привязывает `chat_id` к операции.
4. Пользователь вводит код в приложении → приложение шлёт его в `/auth/poll`.

### `POST /auth/link`

Запрос:
```json
{
  "public_code": "a7f3c9d2e1b4",
  "secret_hash": "sha256:9f2a...",
  "device_name": "Pixel 7",
  "platform": "android",
  "app_version": "1.0.0"
}
```
`secret_hash` принимается и с префиксом `sha256:`, и без.

Ответ `201`:
```json
{
  "public_code": "a7f3c9d2e1b4",
  "deep_link": "https://t.me/free1vpnbot?start=login_a7f3c9d2e1b4",
  "expires_at": "2026-10-05T11:15:55Z"
}
```

Ошибки: `409 public_code_conflict` (код занят активной операцией с другим
секретом), `400 bad_request`.

> **`device_name`**: подтверждено, поле принимается, но на Android его никто
> не заполняет (`AuthViewModel` шлёт пустое). Ничего не сломает — в БД уйдёт
> `NULL`. Просьба к клиенту: передавать `Build.MODEL`.

### `POST /auth/poll`

Запрос:
```json
{ "public_code": "a7f3c9d2e1b4", "secret": "s3cr3t-…", "device_nonce": "4821" }
```

Ответ `200` — подтверждено:
```json
{
  "status": "confirmed",
  "session_token": "V6BR84V7wxhg…",
  "expires_at": "2026-11-04T11:06:03Z",
  "chat_id": 377182640
}
```

Ответ `200` — ещё нет:
```json
{ "status": "pending", "retry_after_ms": 2000 }
```

Другие статусы: `denied`.

Ошибки:

| HTTP | code | Когда |
|---|---|---|
| `401` | `invalid_secret` | секрет не сходится |
| `403` | `nonce_mismatch` | неверный код из бота |
| `404` | `operation_not_found` | операции нет / истекла / исчерпаны попытки |
| `409` | `already_consumed` | сессию уже выдали — «войти заново» |

**`expires_at` в `/auth/poll` — есть** (пробел в контракте закрыт, см. аудит
п. 2). Клиент может читать срок сессии оттуда.

Гарантии: переход `pending → confirmed` ровно один раз; параллельный повторный
poll с верным кодом получает `409 already_consumed`, второй сессии не будет.
Неверный код из бота допускается 5 раз, дальше `operation_not_found`.

## 3. `GET /me`

Ответ `200`:
```json
{
  "chat_id": 377182640,
  "connections_limit": 3,
  "subscription_until": "2026-11-01T12:45:56Z",
  "configs": [
    {
      "id": "GEclient94",
      "name": "Германия · Франкфурт",
      "location": { "country_code": "DE", "city": "Франкфурт" },
      "start_date": "2026-10-02T12:45:56Z",
      "end_date": "2026-11-01T12:45:56Z",
      "status": "active"
    }
  ]
}
```

Три поля из таблицы «чего не хватает» — **добавлены**:

| Поле | Откуда | Примечание |
|---|---|---|
| `connections_limit` | лимит устройств из оплаченного тарифа | для «активно 3 из **N**» |
| `subscription_until` | максимум `end_date` по активным | срок подписки аккаунта, не догадка клиента |
| `id` | имя профиля без `.ovpn` | стабильный идентификатор для `/config/{id}` |

`status` ∈ `active` | `expired` | `revoked`. Список дедуплицирован (в БД бота
одно подключение лежит двумя строками — платной и маркером). Пустой `configs`
— валидный ответ (§3 контракта). Прокси-подключения (`region = proxy:*`) в
список не попадают: это не `.ovpn`.

Ошибка: `401 unauthorized` (токен просрочен/недействителен → экран входа).

## 4. `GET /config/{id}`

Успех `200`:
```
Content-Type: application/x-openvpn-profile
Content-Disposition: attachment; filename="GEclient94.ovpn"
X-Config-Version: 2026-10-02T12:45:56Z
X-Config-Hash: sha256:8401…

<сырой .ovpn>
```

Сервер отдаёт **свежий** профиль: достаёт его с VPN-ноды и минтит одноразовую
ссылку на время запроса. В теле всегда актуальный `.ovpn`.

Ошибки:

| HTTP | code | Поведение клиента |
|---|---|---|
| `401` | `unauthorized` | экран входа |
| `403` | `config_revoked` | «доступ отозван» |
| `402` | `subscription_expired` | «подписка истекла» |
| `404` | `config_not_found` | обновить `/me` |
| `410` | `config_retired` | конфиг снят на сервере |

**`code` присутствует всегда** (пробел аудита п. 1 закрыт): голого `402` без
тела не будет. Проверено живьём: `402 subscription_expired`, `403
config_revoked`, `404 config_not_found`, `401 unauthorized` — все с `code`.

## 5. Что бэкенд по-прежнему НЕ отдаёт

Осознанно, как и просил [README](README.md) §«Чего API не делает»:

- **Нет поля статуса защиты.** Зелёный статус собирается только на устройстве
  (`ProtectionVerdict`). Сервер физически не может породить «защищено».
- Нет скорости, объёма трафика, пинга, числа устройств онлайн.
- Нет призывов к покупке — покупка живёт в Telegram-боте.

Поля срока жизни сборки нет и не будет: обещание с датой остановки сборки снято
2026-10-06 (§2.4). `host:port` для строки «Сервер» сервер не отдаёт — правильный
источник это `remote` внутри `.ovpn` (`§2.3, вариант (а)`).

## 6. Как это устроено на сервере

| Компонент | Где | Роль |
|---|---|---|
| `client-api` (FastAPI) | `127.0.0.1:8006`, unit `client-api.service` | 4 эндпоинта |
| nginx | `194.87.252.181:4443` | TLS + проксирование |
| Бот (`telbot.service`) | MOS | подтверждает вход, показывает `device_nonce` |
| Таблицы входа | `VPN.client_auth_ops`, `VPN.client_sessions` | операции и сессии |

Свежая ссылка на `.ovpn` берётся из Control API платформы
(`POST /api/v1/ovpn/resolve-and-generate`) — по имени профиля. Проксирование
через бэкенд бота: клиент ходит только на `:4443`, до платформы он не достаёт.

Проверка живости: `GET https://194-87-252-181.sslip.io:4443/health` →
`{"status":"ok","service":"client-api"}`.

## 7. Что осталось за клиентом

Из [data-requirements](2026-10-05-data-requirements.md) §2 — это работа на
стороне Android, сервер её не закрывает:

- `device_name` заполнить `Build.MODEL` (§2.8);
- строку «Сервер host:port» брать из ядра после разбора профиля, а не с сервера
  (`eval.getRemoteHost()`, §2.3);
- список «доступных стран» в плашках — из `configs[]` со `status = active`,
  а не хардкодом (§2.7).
