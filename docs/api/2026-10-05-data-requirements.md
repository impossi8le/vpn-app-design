# Какие данные нужны API — по экранам Android-клиента

Дата: 2026-10-05
Назначение: для каждого экрана приложения зафиксировать, **какие данные он показывает**, **откуда они берутся** и **чего не хватает в контракте**.

Это дополнение к `docs/architecture/2026-10-02-api-contract.md` (далее **К**). К описывает **формат** запросов и ответов — этот документ описывает, **что именно нужно экранам**. К не переписывается: ссылки ниже ведут в его разделы.

Значит: поля, помеченные ниже «нужно добавить», сегодня не имеют источника, потому что их нет ни в К, ни в коде.

## 2. Данные, которых нет в текущем контракте

Главный раздел. Ниже — то, что экраны показывают, но чего сервер **сегодня не отдаёт**.

### 2.1 «Подключений активно 3 из 5» — лимит на аккаунт

`AccountScreenState.totalConnections` (`AccountScreen.kt:68`), в макете — «3 из 5» с подписью «2 истекли».

- Активные и истёкшие **считаются из `/me`**: `activeConnections` = число `status == active`, `expiredConnections` = число `status == expired`. Это **считается на устройстве**.
- **Лимит (число 5) в К отсутствует.** Ни в `ConfigList`, ни в `ConfigSummary` нет поля лимита. Отдельного эндпоинта аккаунта тоже нет.
- **Нужно добавить**: `limit` (или `connection_limit`) — либо в ответ `/me` на верхнем уровне, либо в новый `GET /me`-аккаунт. Без него клиент покажет «3 из ?».

### 2.2 «Подписка до 28.10.2026» — срок подписки аккаунта

`AccountScreenState.subscriptionUntil` (`AccountScreen.kt:69`), подпись «Подписка до 28.10.2026».

- В К есть только `end_date` **у каждого подключения** (§3). Подписки как сущности аккаунта в контракте нет.
- Вариант «взять максимум `end_date` по активным» возможен, но это **догадка клиента**, а не факт сервера, и ломается при нескольких подписках с разными сроками.
- **Нужно добавить**: поле срока подписки аккаунта (например, `subscription_until` в `/me`). Если решено считать как максимум `end_date` — зафиксировать это в К явно, а не оставлять на клиент.

### 2.3 «Сервер 185.…​.42:1194 · NL» — адрес и порт сервера

Блок «Защита» на экранах 4, 5, 14б показывает сервер и порт. В коде `ProtectionBlock.server` (`StatusPresentation.kt:48`) **никогда не заполняется** — строка «Сервер» не имеет источника ни в одном из трёх мест.

- В `GET /me` (§3) сервера/порта нет: там `location` — только страна и город.
- В коде тоже нет парсинга: `Config.kt` хранит сырые байты `.ovpn` (`Profile.raw`), но **адрес `remote` из них не извлекается**.
- Правильный источник — **сам профиль**: строка `remote <host> <port>` в `.ovpn` (реальный конфиг проекта содержит `remote` с тремя токенами). Значит, это **можно посчитать на устройстве парсингом профиля** — тогда контракт трогать не нужно.
- **Решение нужно принять** (см. §5): либо (а) клиент парсит `remote` из `.ovpn` — изменений в К нет; либо (б) сервер дублирует `host`/`port` в `GET /me`, чтобы строка была доступна до скачивания профиля. Сейчас не сделано ни то, ни другое.

### 2.4 «Перестанет работать 29.12.2026» — срок жизни сборки

`AccountScreenState.buildExpiryDate` (`AccountScreen.kt:70`), баннер экрана 17.

- О сервере речи нет: TestFlight/тестовая сборка **гаснет по встроенной в неё дате**. Это свойство **самой сборки**, а не аккаунта.
- Сегодня это **локальная заглушка** `"—"` (`AppRoot.kt:238`). Значения из сервера нет.
- **Рекомендация**: оставить **локальной константой сборки** (дата вшита в артефакт при выпуске) — тогда это «считается на устройстве», а не «нужно добавить в контракт».
- **Альтернатива**: если датой надо управлять централизованно (гасить сборки принудительно), **нужно добавить** поле `build_expires_at` в ответ аутентификации/`/me`. Тогда сервер сможет сдвигать дату без перевыпуска APK.
- **Пока в коде** — заглушка; требует решения Архитектора.

### 2.5 Счётчик сессии «04:12:38» и «сессия 04:12:38»

Длительность сессии туннеля.

- Ни в К, ни в коде источника нет. Источник правильный — **локальный таймер** от момента поднятия туннеля. Серверу он не нужен и знать его сервер не должен.
- **Считается на устройстве.** В коде ещё не реализован, но контракт менять не требуется.

### 2.6 «проверено 14:03» и «Kill switch включён»

- `ProtectionBlock.checkedAt` (`StatusPresentation.kt:53`) и `killSwitch` (`:51`) в `ConnectionScreen.kt:248` показываются, но в коде **не заполняются**.
- `checkedAt` — время последнего замера, **считается на устройстве** (локальные часы).
- Состояние kill switch — **факт платформы (VpnService), а не сервера**. Сервер не может знать, включён ли kill switch на телефоне. Максимум — знание, что профиль его настраивает, но не факт его активности.
- **Нужно дореализовать на устройстве**, контракт не меняется.

### 2.7 «Турция и Финляндия доступны — они могут подключиться быстрее»

Плашка на экранах 3б и 15, строка в `escalationPresentation` (`VpnSheets.kt`) — **захардкожена**.

- Список доступных стран у клиента **уже есть**: это `configs[]` из `/me` со `status == active`. Значит, список можно **считать на устройстве**, а захардкоженный текст заменить на реальные имена.
- Дополнительных полей не нужно. Но если сервер должен рекомендовать «быстрое» подключение (метрика нагрузки), это **нужно добавить** отдельно — сейчас такого поля нет.

### 2.8 Имя устройства и версия приложения — уже уходят на сервер

`AuthApi.startLogin` (`AuthApi.kt:36–42`) шлёт `device_name`, `platform = "android"`, `app_version`. Это **есть в контракте** (§1).

- Важно: `device_name` в `AuthViewModel` (`AuthViewModel.kt:47,60`) приходит аргументом, но **на Android никто его не заполняет** — риск пустого поля (зафиксировано в `docs/api/2026-10-05-contract-audit.md`). Это не пробел контракта, а пробел клиента.

## 3. Что считается на устройстве, а не приходит с сервера

Частая ошибка — ждать эти данные от API. Сервер их **не отдаёт**:

| Что | Где | Как считается |
|---|---|---|
| Таймер сессии «04:12:38» | экраны 5, 12, 17 (макет) | локальные часы от момента поднятия туннеля |
| Секуперы подключения «3 сек», «2 сек», «24 сек» | экраны 3, 6, 15 | локальный таймер от старта попытки |
| Пороги эскалации 10/20/30 с | `VpnSheets.kt:324` | чистая функция `escalationStage(seconds)` |
| «осталось 42 дня» | `ConfigMapping.kt:64` | разница `end_date − now`, целые дни |
| «Истёк 30.09.2026» / «до 12.11.2026» | `ConfigMapping.kt:35–42` | форматирование `end_date` устройства |
| Статус подключения (подключено/ошибка) | `ConnectionStatus` | состояние туннеля + замер |
| Статус защиты | `ProtectionVerdict` | **только замер**, см. §4 |
| Число активных/истёкших | `ConfigsViewModel.activeCount` | счёт по `status` из `/me` |
| Обратный отсчёт входа «Осталось 4:37» | экран 1б | от `expires_at` из `/auth/link` |
| Прогресс/загрузка списка | `ConfigsUiState.Loading` | локальное состояние запроса |
| Дата смерти сборки | экран 17 | локальная константа сборки (§2.4) |
| Чекбокс «Больше не спрашивать», тумблеры аккаунта | экраны 11, 12 | локальные настройки (`AccountScreenState`) |

Сервер отдаёт для них только **входные данные** (`end_date`, `expires_at`) или ничего; вывод — на клиенте.

## 4. Данные, которые НЕЛЬЗЯ получать с сервера

**КРИТИЧНО.** Статус защиты («защищено») **не приходит с сервера и не может приходить** — он определяется только реальным замером на устройстве.

Почему:

- Если бы сервер сообщал «защищено», это была бы **непроверяемая ложь**. Сервер не видит, идёт ли трафик конкретного телефона через туннель: он может знать только, что клиент к нему подключился, но не то, что маршруты и DNS на устройстве реально заведены внутрь.
- Клиент **физически не может** показать серверное «защищено»: тип `ProtectionVerdict` имеет **единственный конструктор зелёного** — `ProtectionVerdict.evaluate` (`android/core/domain/src/main/kotlin/com/impossi8le/vpnapp/domain/protection/ProtectionVerdict.kt:36`), — и тот требует **три измеренных факта одновременно**: `ipv4InTunnel`, `ipv6Closed`, `dnsInside`. Все три читаются **из активного линка устройства** (`LinkFacts.kt:14–52`), а не из сети.
- Конструктор доказательства `ProtectionEvidence` — `internal` (`ProtectionVerdict.kt:9`). Вне `core:domain` собрать «зелёное» невозможно: у сетевого модуля (`AuthService`/`ConfigService`) нет доступа к `ProtectionVerdict` (явно зафиксировано в `MockApi.kt:26–31`).
- Единственный владелец перехода в зелёное — `ProtectionGate.evaluate` (`ProtectionGate.kt:24`), и он вызывает **пробу устройства**, а не API.

Следствия — **эти данные нельзя тянуть из API**, их источник только устройство:

- Подтверждение защиты (зелёное) и все три его факта: IPv4 в туннеле, IPv6 закрыт, DNS внутри.
- Состояние kill switch (факт платформы, §2.6).
- Результат проверки «пройдена/не пройдена» (экран 14б).

Если сервер добавит поле вида `protected: true` — клиент **обязан его игнорировать**: показать его как защиту нельзя по конструкции типа (см. архитектуру, §6). См. также `docs/architecture/2026-10-02-vpn-app-architecture.md` §6.

## 5. Что нужно серверу отдать для каждого из 18 состояний

Включая отказные. «Отдать» = какой ответ приводит экран в это состояние.

| № | Состояние | Что должен вернуть сервер |
|---|---|---|
| 1 | Вход | Ничего для отображения; при нажатии — принять `POST /auth/link` и вернуть `public_code`, `deep_link`, `expires_at` |

| 6 | Смена страны | `GET /me` с несколькими `active`-подключениями |

| 8 | Отказ в разрешении | Ничего (системное состояние) |

| 10 | Всё истекло | `GET /me`, где **все** `configs[].status = expired` (список непустой) |

### Сводка: что **нужно добавить** в контракт

1. **Лимит подключений на аккаунт** — для «3 из 5» (`totalConnections`). Сейчас нет. → `limit` в `/me` или новый эндпоинт аккаунта.
2. **Срок подписки аккаунта** — для «Подписка до 28.10.2026» (`subscriptionUntil`). Сейчас нет; максимум `end_date` — догадка клиента. → `subscription_until` в `/me`.
3. **Дата смерти сборки** — для «Перестанет работать 29.12.2026» (`buildExpiryDate`). Либо **локальная константа сборки** (тогда не поле контракта), либо `build_expires_at` в ответе входа/`/me`. Решение Архитектора.
4. **Адрес сервера (host:port)** — для строки «Сервер» в блоке «Защита». Либо **парсить `remote` из `.ovpn` на устройстве** (контракт не меняется), либо дублировать в `/me`. Сейчас нет нигде.

Всё остальное на экранах либо **уже есть в контракте** (`/auth/link`, `/auth/poll`, `/me`, `/config`), либо **считается на устройстве** (§3), либо **запрещено получать с сервера** (§4).
