# Доказательства: «Подключено» при мёртвом туннеле

Собрано 2026-10-06 на живом телефоне Samsung SM-S928B (Android 16), сборка
release v98 (versionCode 98).

## Что показывает приложение

Экран главный, состояние:

```
text="Подключено"
text="Подключено, часть трафика идёт напрямую: сервисов — 4"
```

## Что показывает система в тот же момент

```
$ adb shell ip -brief addr show tun0
Device "tun0" does not exist.

$ adb shell ip route get 8.8.8.8
8.8.8.8 via 192.168.3.1 dev wlan0 table 1045 src 192.168.3.162

$ adb shell ip route get 87.240.129.1
87.240.129.1 via 192.168.3.1 dev wlan0 table 1045 src 192.168.3.162

$ adb shell ip route show table all | grep -c tun0
0
```

`dumpsys connectivity` — среди сетей **нет ни одной** с `Transports: VPN`:
только CELLULAR (IMS) и WIFI.

Сервис при этом жив: `dumpsys activity services` показывает
`VpnTunnelService` (8 совпадений).

## Вывод

Туннеля нет: ни интерфейса `tun0`, ни маршрутов через него, ни VPN-сети в
системе. **Весь трафик — в том числе к подсетям обхода — идёт открытым через
`wlan0`.** Приложение в это же время утверждает «Подключено».

## Почему это нарушает §6

§6 запрещает показывать защиту, выведенную из флага, а не из факта. Здесь тот
же класс ошибки, только про «Подключено»: состояние получено один раз по
событию ядра `CONNECTED` и **не перепроверяется**. Когда туннель умирает без
события `Disconnected` от ядра (интерфейс снесла система, сервис пережил
отзыв, ядро замолчало), экран навсегда остаётся в «Подключено».

Проверить состояние нельзя и без телефона: логи ядра пишутся только в debug
(`newSession.onLog` под `BuildConfig.DEBUG`), поэтому в release причины не
видно.

## Что требуется починить

«Подключено» должно опираться на **проверяемый факт существования туннеля**, а
не только на последнее событие ядра. Минимально честный вариант: пока состояние
«туннель поднят», периодически убеждаться, что интерфейс туннеля ещё есть (и
сессия ядра жива), и при исчезновении — переводить в `Disconnected`, а не
оставлять зелёное/подключённое.
